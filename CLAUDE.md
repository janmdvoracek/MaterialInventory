# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MaterialInventory records material **processing jobs** — what a transformation consumed and produced, who worked it and for how long, and which machines ran.

**It no longer tracks stock.** Příjem (receipt), Výdej (shipment) and Úprava (adjustment) were removed along with the stock dashboard, movement history and CSV export, `track_stock`, and every balance/sufficiency check. Nothing sums quantities into an on-hand figure and nothing blocks a job for insufficient material. The one quantity rule left is **within** a single job: a transformation's consumed and produced totals must match (see Architecture), which is mass balance across the form being submitted, not a stock level. Even that has one exemption — a job that records nothing but refuelling; see `_is_fuel_only`. The name is now historical — don't reintroduce inventory semantics because the repo is called MaterialInventory.

## Tech stack

Django 6, PostgreSQL, server-rendered templates, no separate JS frontend. Depot workers fill out mobile-first web forms; Django's admin serves as the back-office UI for managers.

**There is no API, no JavaScript framework, and exactly two scripts of the app's own, both on the job form.** `django_htmx`, `widget_tweaks` and `rest_framework` were all installed but never used — no template carried an `hx-*` attribute or loaded `widget_tweaks`, and there were no serializers, viewsets or API routes — so they are gone from `requirements.txt`, from `INSTALLED_APPS`, and (htmx) from `MIDDLEWARE`, along with the `REST_FRAMEWORK` settings block and the `<script src="https://unpkg.com/htmx.org">` tag in `base.html`. That tag mattered: the deployment was LAN-only when it was removed, so every page load was firing a request at a CDN the depot may not be able to reach. (It is a public VPS now, which makes the CDN reachable again but does not make the tag worth having back — nothing uses htmx.) Reintroducing any of the three means adding the dependency back deliberately, not assuming an established pattern. The rule that tag broke still stands: **the app serves its own scripts out of `static/`, never a third party's off a CDN, and there is no build step, no bundler and no package.json.** `RowTemplateTests` fails if a URL appears in either file.

The first script is **`static/js/job_rows.js`, and it is progressive enhancement — treat that as a hard constraint, not a style.** It resizes a section of the Zpracování form in the DOM, and the „+ další řádek" / „− odebrat řádek" pair it hangs off **remain ordinary submits** that post the form back under `add_<prefix>` / `remove_<prefix>`, which `_job_forms` still answers by re-rendering the page one row bigger or smaller. With the script missing, blocked or broken the form behaves exactly as it did before it existed. **The reason is the test suite**: it drives views through `self.client` and runs no browser, so the server path is the only one it can see and has to stay the source of truth — `RowButtonTests` is testing something real precisely because that path is still reachable. Never move behaviour into the script that only the script can then perform; `RowTemplateTests` covers the contract it reads off the page (the `<template>` per section, the rendered row bounds, `empty_form` escaping `_hide_taken_choices` and honouring `form_kwargs`/`keep`, both pages linking both files) but the script's own behaviour is untested by construction. **The second is `static/js/searchable_select.js`, on the same terms**: it hides each row's `<select>` in the four sections behind a text box that narrows the options as you type. The `<select>` keeps its name and its value and is still what the form posts (`hidden` is not `disabled`); the text box has no `name` and posts nothing, and no view or form knows the file exists. It invents no choices — options, labels, order and the `empty_label` it lifts out as the placeholder are all read off the rendered `<select>`, and read again every time the list opens, which is what makes it agree with `_hide_taken_choices` and with `job_rows.js` for nothing: an option another row took is already `hidden`, and committing a pick dispatches a `change` event so the other rows re-hide it. Matching is case- and diacritic-insensitive (`normalize('NFD')`) so „ster" finds „Štěrk". Rows added by `job_rows.js` are picked up by a `MutationObserver` on the section rather than a call from the other file, so neither script depends on the other being loaded, or loaded first; `<template>` contents are a separate fragment and are never enhanced. `SearchablePickerTests` covers the contract it reads off the page — one `<select>` per row, the valueless `empty_label` first, an id per select, and the three `app.css` rules (`.combo` relative, `.combo-list` absolute, `.combo select[hidden]` hidden) without which the list renders as a bullet list shoving the rows below it down — and, like the other script, its own behaviour is untested by construction. Every other page in the app is still a plain form POST with no script at all. See the Architecture section. All page CSS is one file, `static/css/app.css`, loaded by `templates/base.html`; no template carries an inline `style=` attribute or a `<style>` block of its own. One rule in it is easy to mistake for noise and is not: **`button[hidden], .btn[hidden] { display: none }`**, because `button, .btn` sets a `display` and an author rule beats the UA stylesheet's `[hidden] { display: none }` at any specificity — without it the `hidden` on „− odebrat řádek" does nothing and a one-row section renders a button that cannot work. `RowTemplateTests` pins it. **Every colour in it is a custom property declared twice** - once in `:root` for light, once again under `@media (prefers-color-scheme: dark)` - so a colour literal written into a rule below those two blocks is a bug: it will be right in one theme and wrong in the other. Dark mode follows the operating system setting and nothing else: no toggle, no stored preference, no JavaScript, and `base.html` carries a `theme-color` meta per scheme whose values must be kept in step with `--chrome-bg` by hand. `ThemeTokenTests` in `workorders/tests.py` reads the stylesheet and fails if the two blocks declare different token sets, if a `var()` names a token nobody declared, or if a literal survives below them. The admin ships its own dark theme, driven by the same media query, so it needs nothing.

## Architecture

Modular monolith, one Django project (`config`) with these apps:

- `accounts` — custom `User` model with a `role` field (`WORKER`/`MANAGER`/`ADMIN`), an `is_manager_or_admin` property and a `has_admin_access` one. `accounts/decorators.py::role_required(*roles)` gates privileged views (401/redirect if anonymous, 403 if wrong role). **`accounts/middleware.py::AdminSessionRequiredMiddleware` gates `/admin/` itself**: everything under the prefix is a **404** unless `request.user.has_admin_access`, which is `is_active and is_staff and (is_superuser or role == ADMIN)`. That covers `/admin/login/`, and covering it is the whole point — the deployment is a public VPS, and Django's own admin login form would otherwise be the one page on the internet where guessing a password is worth an attacker's time, sitting at the URL every scanner tries first. The app's own `/login/`, which django-axes rate-limits, is the only login form left. Three things about it. **A 404 and not a redirect to `/login/`**, deliberately: an admin who is logged out is one visit to the app away from getting in, while a redirect would confirm to a scanner that the admin is here — the cost is that `/admin/` typed while logged out looks like a broken URL, which the runbook says to expect. **Its position in `MIDDLEWARE` is load-bearing**: it goes *above* `CommonMiddleware`, because `APPEND_SLASH` turns any 404 for `/admin` into a 301 to `/admin/` — handing back exactly the confirmation the 404 withholds — and above `CsrfViewMiddleware`, so an anonymous POST to `/admin/login/` is a 404 rather than a 403; that puts it above `AuthenticationMiddleware` too, so it resolves the user itself with `django.contrib.auth.get_user` (what that middleware's lazy `request.user` calls) and needs only `SessionMiddleware` above it. Moving it down breaks the slashless case silently, which is why the test suite and the smoke script both check `/admin` without its slash. **The prefix comes from `reverse('admin:index')`**, lazily (the URLconf is not loaded while middleware is built), so mounting the admin elsewhere stays covered; the user is resolved only for paths under it, so no other request pays for the lookup. And **the header link in `base.html` reads the same `has_admin_access`**, not `is_staff`, or a visible „Administrace“ would lead to the 404 the gate serves. `AdminGateTests` and `AdminLinkTests` in `accounts/tests.py` cover both halves, and `scripts/smoke_prod_stack.sh` re-checks the 404 through the built image and Caddy.
- `materials` — `Material` catalog (SKU and name only). `materials/management/commands/seed_data.py` bulk-loads materials/machines/users from CSV (see Commands below) — the one place `materials` imports from `machines`; the two models know nothing of each other. **Line items carry no location**: the old per-row `StockMovement.location`, its form column and `locations.csv` were removed and stay removed. A line item records *what*; *where* is now a property of the whole job — see `locations`.
- `machines` — `Machine` (name, `is_active`, and two optional rates, `hourly_rate` in Kč/hod and `rate_per_ton` in Kč za tunu zpracovaného materiálu — **both now price the Stroje summary**, see `_machine_costs`). It was split out of `materials` while production held no data, so the move was a migration reset rather than a table rename; each app carries its own `RETIRE_HELP_TEXT`, worded for a material or a machine. `MachineUsage` and `MachineRefuel` deliberately stay in `workorders` — both are rows of a job, not catalog data, and moving them would make the two apps import each other.
- `locations` — `Location` catalog (name and `is_active`, with its own `RETIRE_HELP_TEXT`), maintained **in the admin only** — there is no CSV and `seed_data` does not touch it. `WorkOrder.location` points at it: **one location per job, and it is a label, not a stock location.** Operators work at several sites, some keeping their material records separately and some keeping none; the field says which site a job belongs to, and nothing is balanced, summed or refused per location — the mass balance is identical everywhere. The FK is `PROTECT` and **nullable** (jobs recorded before the column, and fuel-only jobs, have none; pages print „—", the Materiál detail CSV a blank cell). It is **required on every work job** through `WORK_FIELDS` — see the „Popis" / „Moje hodiny" paragraph below — and retired like a machine: unticking `is_active` drops it from the picker, and `job_edit` passes the job's own one as `keep_location` through the same `_offer_recorded`. It is shown and filtered on **Přehled and Materiál only** (`JobFilterForm.location`, `MaterialFilterForm.location` via `work_order__location`, „Všechny lokace"), on the job detail page and in the Materiál detail export; Hodiny and Stroje ignore it. The form field is a plain `<select>` — `searchable_select.js` enhances only the four sections. `LocationTests` covers it.
- `workorders.StockMovement` — one material line item on a job: what it consumed, as a negative quantity, or produced, as a positive one. `movement_type` is `TRANSFORM_CONSUME` or `TRANSFORM_PRODUCE` — nothing else. **A line item has no timestamp of its own** — its date is its job's `performed_on`, and `Meta.ordering = ['id']` keeps a job's rows in the order they were typed. **`StockMovement` is not registered in the admin**: a line item never exists apart from its job, and `WorkOrderAdmin` already edits the rows as an inline, so registering it as well put a second top-level section in the index — labelled `Zpracování`, like the worker form, and holding one model reachable from Zakázky anyway. Everything about a job is edited in one place, and `AdminIndexTests` in `accounts/tests.py` asserts the section stays gone. **`MachineRefuel` is not registered either, for the same reason** — it is a row of a job, edited through `MachineRefuelInline`.
- `workorders` — **the whole app, effectively.** `WorkOrder` groups the `StockMovement` line items from a single transformation job, plus a `collaborators` M2M. One submission also writes one `WorkerHours` row per participant, any number of `MachineUsage` rows (chained machines supported) and any number of `MachineRefuel` rows, all in a single `transaction.atomic()` — the four record types are one job and must not land half-written. **No section of the job form may name the same thing twice**: one material per section, one machine, one person. `UniqueChoiceFormSet` in `workorders/forms.py` is both halves of that — `clean()` refuses a repeat and puts the Czech complaint on the *repeated* row (the whole job is refused, like the mass balance below), and `_hide_taken_choices()` keeps what other rows already took out of a row's dropdown so it is not offered in the first place. The hiding runs on **unbound** formsets only: narrowing a bound one would turn a duplicate into „Vyberte platnou možnost." instead of the real message, and every row keeps its own choice or it would render blank. Server-side it can only be as fresh as the last render — the list was built when the page was, and the renders that matter are „+ další řádek" and the edit form's spare row; `job_rows.js` narrows the same lists live as the dropdowns change, but it may not be running, and picking the same thing twice between two renders is what `clean()` is there for either way. **One asymmetry falls out of the two together, and it is expected**: a server-rendered row had the taken options `exclude()`d from its queryset, so they are not in the DOM and freeing one up again cannot bring them back — the script can only hide what is there, while a row the script added carries the whole catalog and does behave that way. Don't "fix" it by dropping the server-side narrowing; that costs the feature entirely to anyone whose browser never ran the script. The rule is **per section**, so one material may still be consumed *and* produced by one job. Formset rows are otherwise written exactly as typed — nothing is combined on the way in, because with duplicates refused there is nothing to combine (`_collect_rows` used to sum repeated worker rows and no longer does). `DuplicateRowTests` covers it. **A job must balance: it needs at least one consumed row and one produced row, and the two sums must be exactly equal** — `transform_create` compares `sum(consumed)` against `sum(produced)` before opening the transaction and re-renders with a Czech `messages.error` if they differ. **The one exemption is a fuel-only job** (see the `MachineRefuel` paragraph below): it has no two totals to compare, so `_valid_job_rows` returns early on `_is_fuel_only(rows)` rather than passing a balance of zero against zero. Totals, not row-by-row: one input is normally crushed into several output fractions. Exact `Decimal` equality, no tolerance, so `5.00` and `5` pass but `5.01` and `5` do not. The form's `quantity` accepts 2 decimal places while `StockMovement.quantity` stores 3 — a form tighter than its model is fine and needs no migration, but it means the tightest mismatch the check can be tested against is `0.01`, not `0.001`. **A form *wider* than its column is a different matter, and the three `hours` fields are the place to watch**: `WorkerHours.hours` and `MachineUsage.hours` are `decimal(12, 2)`, so ten integer digits, and a value past that passes form validation, reaches the INSERT and comes back as `DataError: numeric field overflow` — an unhandled 500, not a message on the field. They are therefore capped at `HOURS_MAX_DIGITS` in `workorders/forms.py`, which is **11 and not 10**: `DecimalValidator` allows `max_digits - decimal_places` integer digits, so ten of those plus the one decimal place the fields accept is eleven. Off by one either way is a real bug — 12 is the overflow, 10 refuses a value that stores fine. `quantity` and `tons` need no cap, being `max_digits=7` against far wider columns. `HoursWidthTests` pins both edges. The check has no database state behind it, which is why it sits in the view ahead of the write rather than in a model `clean()`. **A job carries two text fields and they are deliberately different shapes.** `WorkOrder.description` („Popis") is a **required** (except on a fuel-only job) `CharField(max_length=255)` on a single-line input — it is the job's label and the „Zakázka" column on Přehled, Hodiny, Stroje and Materiál, plus a column of the Materiál detail export, so a job without one is a blank cell in four places. `WorkOrder.notes` („Poznámky") is the **optional** long one: a `TextField` behind a four-row `<textarea>`, shown only on the job detail page through `linebreaksbr`, and read by no list column, no filter and no export — it is prose, and none of those are prose columns. The form caps `notes` at `NOTES_MAX_LENGTH` (2000) though the column has no limit; that is the allowed direction (tighter than the model, no migration) and turns a pasted document into a field error rather than an unbounded row — the opposite direction is the `hours` overflow the `HOURS_MAX_DIGITS` cap exists for. Both sit in `_job_form_fields.html`, so both pages get them at once, and both render their errors. Rows recorded before „Popis" became required may still hold an empty one; nothing backfills them and the pages still print „—", and so does a fuel-only job. **„Popis", „Moje hodiny" and „Lokace" therefore all carry `required=False` on the form and are re-imposed by `_require_work_fields` (they are `WORK_FIELDS`) once the rows are known**, because the form on its own cannot tell a job that records work from one that records a tank of diesel. The error is the field's own `error_messages['required']`, not a hardcoded Czech string, so it reads like every other required field and comes out of the same catalog. `DescriptionAndNotesTests` covers both fields and `MachineRefuelTests` the exemption. **A job carries the date it was performed**, `WorkOrder.performed_on`, separate from `created_at` (when it was typed in). `WorkOrderForm.performed_on` is a required date field **pre-filled with today** (`initial=timezone.localdate`), so the common case is already answered and back-dating means editing the box. An empty or future date is a form error, so nothing at all is written. `job_edit` shows the job's own date, not today, so a correction that touches nothing else does not move it. Day only, no time: `<input type="date">` renders the same everywhere, while the `datetime-local` widget the removed Příjem/Výdej forms used let an English phone show AM/PM under `lang="cs"`. **The widget carries an explicit `format='%Y-%m-%d'`** — this is the one form in the app with an unbound date field holding a python `date`, and without it the value renders through the `cs` `DATE_INPUT_FORMATS` as `02.09.2026`, which `<input type="date">` rejects outright and shows as an empty box. Two tests assert the rendered `value=`. **Every report keys off it.** The date filters on Hodiny, Stroje, Materiál and Přehled compare `performed_on` (a `DateField`, so a plain `__gte`/`__lte` — no `__date` lookup and no timezone conversion), every "Provedeno" column shows it, and ordering is `[-performed_on, -created_at]` — on the four lists *and* in `WorkOrder.Meta`. **Machine-usage and line-item rows are dated by their job**, `work_order__performed_on`, not by `MachineUsage.created_at`: `job_edit` deletes and rewrites every row, so a corrected job would otherwise drift to the day it was corrected. A `StockMovement` has no timestamp of its own at all, so its job's date is the only one there is. The one list still ordered by `-created_at` is `my_jobs` — it is a recency list of *submissions*, and a job just back-dated to last month has to appear at the top of it, which is the whole reason a worker opens it; its date column still shows `performed_on`. `created_at` survives as "when it was typed in" on the job detail page („Zaznamenáno"), the edit and delete pages, and the admin. The totals in that error message go through `django.utils.formats.localize` — an f-string would print `9.5` where the rest of the UI shows `9,5`. Beyond the Transform form there are three read-only views: **Stroje** (`machine_dashboard`), **Materiál** (`material_dashboard`) and a per-person time-worked report (`time_worked`). All three are built the same way — one filter driving a summary table and the detail rows it is made of; Stroje does it twice, once for runtime and once for fuel. Stroje sums motohodiny and tonnage per machine, shows both rates, **prices the two against each other in three money columns**, then lists the individual `MachineUsage` rows underneath. Those columns — „Cena za hodiny", „Cena za tuny", „Celkem" — are `_machine_costs`, applied per row in Python (which is why `_machine_summary` returns a **list**, not a queryset: the rule is conditional and a `Case`/`When` over an aggregate would be far harder to read for a table of one row per machine). Two rules, both of which come down to telling *unknown* apart from *zero*, the same distinction `MachineUsage.tons` already forces: **an unset rate means the machine is not priced that way, not that it is free**, so that side is a dash — while `filtered_hours` is a real zero, so a priced machine that did not run in range costs `0,00`, not a dash. And **„Celkem" adds up only the sides the machine is priced on and is itself unknown when any of them is**: a machine billed per tonne whose usage predates the `tons` column has a cost nobody can compute, and printing the hours half of it under „Celkem" would understate the bill. In the CSV all three go out through `_csv_number`, so an unknown is a blank cell rather than a `0` that Excel would sum as a free machine. **Materiál is the only page that reads the line items back across jobs**: `_material_summary` annotates every active `Material` with `filtered_consumed` / `filtered_produced` / `filtered_net` over the rows the page's own filter allows, and `_filtered_material_movements` lists those `StockMovement` rows below. Because `quantity` is stored signed, the net is just the unfiltered `Sum` — no subtraction and no second query — and `filtered_consumed` is wrapped in `Abs` for the same reason `_job_line_items` takes `abs()`: the form asked for a positive number and that is what the reader should see. The zeros are real zeros here, not the unknown that `MachineUsage.tons` renders as `—`, so a material with no rows in range reads `0,00 t` (`Coalesce` on the net, `|default:"0"` on the two sides). It is `role_required(MANAGER, ADMIN)` like Stroje, and its `MaterialFilterForm` deliberately has no `created_by` — who typed a job in is a review question, not a material one — but does have `location`, since separating one site's material from another's is exactly a material question. Plus the review pages described next.

  **Every summary table on those three downloads as a CSV, and so does Materiál's detail table.** `machine_dashboard_export`, `material_dashboard_export` and `time_worked_export` sit at `<page>/export/` and are linked by a „Stáhnout do CSV / Excelu" button at the foot of the summary card, carrying the page's own `querystring` so the file is the table that was on screen. **Stroje has two, because it has two summary cards**: `machine_refuel_export` at `machines/fuel/export/` is „Tankování", built from `_filtered_machine_refuels` + `_refuel_summary` on the same terms as the rest. **`material_detail_export` at `materials/detail/export/` is the one row-level download**, linked the same way under „Detail položek": those line items are the only place in the app that says what a single job consumed and produced one line at a time, which is what reconciling a month against delivery notes needs, whereas Stroje's usage rows have no reading the totals do not already give — so they stay unexported, and so do its fill-ups and Hodiny's rows. **The detail file is every row the filter allows, not the page on screen** (the table paginates at `HISTORY_PAGE_SIZE`; a file holding rows 1–50 of 300 under the heading of the whole filter is worse than no file), a trap the summaries do not have, being one row per material or machine. **Each export is built from the same helpers as its page** (`_filtered_machine_usages` + `_machine_summary`, `_filtered_material_movements` + `_material_summary`, `_filtered_material_movements` alone for the detail, and `_time_worked_scope`, which was extracted out of `time_worked` for exactly this), so a download can never disagree with the table it was started from: pending jobs stay out of it, and an invalid filter exports a header row and nothing else rather than the whole report. Each carries the same gate as its page — `time_worked_export` is `login_required` and the other four are `role_required(MANAGER, ADMIN)`, the detail file being the one most worth gating since it names every job's author and description — and the worker scoping that makes a worker's download their own hours rather than the depot's lives in `_time_worked_scope`, not in the view, which is the point of the shared helper. **One file answers both halves of „csv/excel", with no new dependency** (openpyxl would buy formatting nobody asked for): `_csv_response` writes `;`-delimited rows behind a UTF-8 BOM. Both are about Excel under `cs` — it splits a `.csv` on the *locale's* list separator, so a comma-delimited file lands in one column, and without the BOM „Štěrk" opens as mojibake. Numbers go through `django.utils.formats.number_format`, so a tonnage arrives as `12,50` and is summable rather than text. `_csv_number` renders an *unknown* — a `None` tonnage, an unset rate — as a **blank cell** and not the page's `—`, because a dash is text that breaks a numeric column, while blank stays out of a `SUM`; a real zero is passed in by the caller (`filtered_hours or Decimal('0')`), matching the `|default:"0"` in the template. The same goes for text on the detail file — a job with no description exports an empty cell, not the page's `—` — and its „Provedeno" column goes out as `performed_on.isoformat()`, matching the page, which writes its dates with an explicit format for the same locale reason. `TableExportTests` in `workorders/tests.py` covers the format, the filter round-trip, the gating, and that the detail file is the whole filtered set rather than one page.

The app is five pages: **Zpracování** (`transform_create`, mounted at `/` and the landing page), **Hodiny** (`time_worked`), **Stroje** (`machine_dashboard`), **Materiál** (`material_dashboard`) and **Přehled** (`job_dashboard` at `/jobs/`, with its detail/edit/delete pages). Three of those five also answer at `<page>/export/` with a CSV of their summary table — Stroje twice, at `machines/export/` and `machines/fuel/export/`, one per summary card — and Materiál answers at `materials/detail/export/` with its line items — downloads, not pages: no template, no nav entry, and nothing to add to the bottom nav. There is no separate machine-history page any more — `machine_usage_history` and its template were folded into Stroje, because the totals and the rows behind them are the same data at two zoom levels and splitting them across two URLs meant filtering twice. `workorders/urls.py` is mounted at the root in `config/urls.py`; no other app contributes a URL. **The views are split across two modules**: `workorders/views.py` records and reviews jobs (Zpracování and `/jobs/`), and `workorders/reports.py` holds Hodiny, Stroje, Materiál, their CSV exports and the list-page helpers (`_list_page_context`, the date presets) that `job_dashboard` imports. `REVIEWER_ROLES`, which both gate on, lives in `accounts/decorators.py` beside `role_required` — in either module it would make the two import each other. **The reports stay a module of `workorders`, not an app of their own — that was considered and decided against.** Every report only aggregates the four job models and filters to approved jobs, their filter forms live in `workorders/forms.py`, and `job_dashboard` imports `_list_page_context` from them, so a `reports` app would depend on `workorders` entirely and need shared helpers moved out just to avoid a circular import — migrations, settings and URL churn for no change in behaviour. Revisit only if the reports get a separate audience or deployment.

**A job does not count until it is approved.** `WorkOrder` carries `status` (`PENDING`/`APPROVED`), `reviewed_at` and `reviewed_by`. `transform_create` writes a worker's submission as `PENDING`; a manager's or admin's own submission is written `APPROVED` with themselves as reviewer, because there is nobody above them to sign it off. **`time_worked`, `machine_dashboard` and `material_dashboard` all filter to `status=APPROVED`** — a pending job is recorded but invisible in every report, including to its own author, so the submit message tells the worker it is waiting. The review pages are `job_dashboard` / `job_detail` / `job_edit` / `job_approve` / `job_delete`, all under `/jobs/` and all gated with `@role_required(MANAGER, ADMIN)`. **There are exactly three review actions — schválit, upravit, smazat.** A job is never handed back to its author: there is no `RETURNED` status, no `review_note` and no `job_return` view. **Only a manager edits a job**, and editing deliberately does *not* approve. What a worker *does* get is `my_jobs`, built by `_my_recent_jobs` and rendered at the **top of Hodiny** (not the Transform form): their own last `MY_JOBS_LIMIT` (5) submissions with a status badge and their own hours (`Sum('worker_hours__hours')` filtered to that user). **That list is the only feedback on the review anyone gets** — a pending job is invisible in every report, so without it there is no telling one awaiting approval from one that never landed; it lives on Hodiny because that is the page the withheld hours are missing from. Three scoping rules, each with a test: it is scoped by `created_by` alone, deliberately *not* by `participation_filter` (being named on someone else's job is not recording one, and those hours surface in the summary once approved); the `TimeWorkedFilterForm` filters do **not** apply to it, since they scope the approved-hours report and a pending job is exactly what that report cannot show; and `_my_recent_jobs` returns `none()` for a manager or admin, whose Hodiny is the whole depot's report and who have Přehled already. `job_edit` goes through the submission's own helpers (`_job_forms`, `_valid_job_rows`, `_write_job_rows`), so a correction is mass-balanced exactly like the original, and it writes the rows as the **author** (their hours in „Moje hodiny", `collaborator_queryset` built from the author *and* the editing manager so it excludes the author and not the manager, `created_by=author` on the movements). **`job_edit` also widens the three catalog pickers to whatever the job already names**, `is_active` or not. Scoping them to the active catalog is right on a new job and a data-loss bug here: a `ModelChoiceField` whose queryset excludes the stored pk renders the row with nothing selected, and saving the form as rendered posts an empty row — which, since `_write_job_rows` clears and rewrites, deletes the machine usage outright while still reporting success, and leaves a job whose consumed row vanished stuck behind a balance error no edit can clear. `job_edit` collects the pks by section prefix from the line items and machine usages it has loaded, `_section_form_kwargs` passes them as `keep`, and `_offer_recorded` in `forms.py` unions them back in. **Only what that job names comes back** — the rest of the retired catalog stays hidden and a fresh form passes no `keep`, so retiring something still means something. The workers section needs none of it: `collaborator_queryset` never filters on `is_active`. `RetiredCatalogOnEditTests` covers it.

**`WorkerHours` (labour) and `MachineUsage` (runtime) are two unrelated numbers** — don't derive one from the other. `WorkerHours` is what a person typed for themselves on the Transform form: the submitter's own hours come from `WorkOrderForm.hours` ("Moje hodiny", required), and each collaborator's from a row in the workers section. `MachineUsage.hours` is motohodiny for a machine, `MachineUsage.tons` is how much material that machine put through on the job — a third independent number — and `MachineRefuel.litres` is a fourth. **Tonnage is not part of the mass balance**: chained machines each process the same material, so the machine rows sum to a multiple of the consumed total, and nothing compares them. `tons` is required on any machine row that names a machine, but nullable in the model, because rows written before the column existed have no answer (unknown, not zero); the usage rows render those as a dash, and so do the per-machine totals — `Sum` skips NULLs, so a machine whose usage all predates the column sums to `None` and shows `—` rather than a `0 t` that would read as "processed nothing". The Hodiny tab reports only `WorkerHours`, so its total has no fixed relationship to the motohodiny on Stroje.

**`MachineRefuel` is fuel, in litres, and it is its own table rather than a `litres` column on `MachineUsage`.** The reason is not tidiness: the two rows do not imply each other. A machine can be refuelled on a job it did not run — a whole job can be nothing but tanking up — so a fill-up has to exist with no usage row beside it, and `MachineUsage.hours` is not nullable so there would be nothing to hang the litres off. Like every other row on a job it carries **no timestamp of its own** (its date is the job's `performed_on`, since `job_edit` rewrites every row) and it **cascades** when the job is deleted. Unlike `tons`, `litres` is **not nullable**: the column is new, but a fill-up row only exists because someone typed a number into it, so there is no *unknown* to represent and a `Sum` of `None` can only mean „no fill-ups in range" — which is why the Tankování card reads `0,00 l` where the tonnage column reads „—". Nothing derives litres from hours or tonnage, and litres are not part of the mass balance.

**Both live on the *Použité stroje* section, which is now four fields wide** (stroj, motohodiny, tuny, natankováno), and `MachineUsageForm` is therefore the one row form that does **not** follow `RowForm`'s all-or-nothing rule: it overrides `check_row`, the hook the rule moved into (`RowForm.clean()` keeps the early return on `self.errors` that stops a row's own complaint printing over a field error). Motohodiny and tuny still go together; litres stand alone. So „stroj + hodiny + tuny" is a usage row, „stroj + litry" is a fill-up and no usage row, all four is both from one row, while one of hours/tons alone, a machine with nothing beside it, and litres with no machine are each refused with their own Czech message. `_collect_rows` returns a `JobRows` NamedTuple splitting the section into `usages` (rows with motohodiny) and `refuels` (rows with litres), and `_write_job_rows` writes each to its own table. The no-duplicates rule is untouched and covers both halves at once, so a machine refuelled twice on one job is one row carrying the sum. **`job_edit` has to put the two tables back together**: `_machine_section_rows(usages, refuels)` merges them into one row per machine, and `keep` collects the machines named by *either*, or a retired machine that only a fill-up names renders with nothing selected and the fill-up is dropped on save while the page reports success — the same data-loss trap `RetiredCatalogOnEditTests` covers for the usage rows.

**A submission carrying nothing but fill-ups is a complete, valid job**, and that is the point of the field: someone tanks up three machines and records it, with no transformation involved. `_is_fuel_only` is true when there is at least one fill-up and no consumed rows, no produced rows, no motohodiny and no collaborator hours, and such a job is exempt from the mass balance, from „Lokace", from „Popis" and from „Moje hodiny" — that last one could not be answered honestly anyway, its minimum being half an hour, so `own_hours` is `None` and **the author gets no `WorkerHours` row at all**. It stays an ordinary `WorkOrder` otherwise: dated, authored, `PENDING` until approved, and listed on Přehled. Not being *asked* for a description is not the same as refusing one, so a worker who types one keeps it. Add any motohodiny or any material row and every one of them comes back. `MachineRefuelTests` covers all of it.

**A manager or admin can record a job for someone else.** `WorkOrderForm` grows an `author` field („Zapsat za", `empty_label='Za sebe'`) for them and only for them — a plain worker's form has no such field, so an `author` in their POST is never cleaned and the view has nothing to defend against. When set, the job is written with `created_by=author` and `_write_job_rows(..., author, ...)`, so the hours, the line items and „Moje hodiny" all belong to that person; the field also relabels `hours` to „Odpracované hodiny", since „Moje" would be wrong half the time. **Approval still follows the submitter, not the author**: a manager typing a worker's job in is the reviewer and has just seen the work written down, so it is `APPROVED` with `reviewed_by=<the manager>` and `created_by=<the worker>`. Because the author decides who may be named as a collaborator, `transform_create` settles it with `_submitted_author` before any formset is built — on a submission and a row-button rebuild alike.

`collaborator_queryset(user, viewer=None)` therefore takes **two** people: `user` is the job's author and is excluded from the list (you cannot collaborate with yourself), while `viewer` — whoever is filling the form in — decides how wide the list is. They differ only when a manager acts for someone else, and then the manager's privilege applies: the workers-only restriction exists to stop a *worker* putting hours on a manager, not to stop a manager recording that a manager worked the job. `job_edit` passes the same pair (author + the editing manager). A plain worker recording their own job is unaffected: `viewer` defaults to `user` and the old rule holds.

`collaborators` is **derived**, not entered: `transform_create` calls `work_order.collaborators.set(worker_hours.keys())` so the M2M can never disagree with the hours rows about who worked the job. Naming the same person on two rows is refused by `WorkerRowFormSet` (see the no-duplicates rule above), which is what keeps the `unique_worker_hours_per_work_order` constraint out of reach — it used to be avoided by summing the two rows instead. `collaborator_queryset` in `workorders/forms.py` excludes the job's author (you can't collaborate with yourself) and, when a plain worker is the one filling the form in, anyone who isn't also a `WORKER` — see the two-argument rule above. The one place the two *can* drift is the admin: `WorkOrderAdmin` exposes the `collaborators` multi-select and the `WorkerHoursInline` as independent widgets, so an admin edit can leave a collaborator with no hours row, or vice versa.

**A machine stores no totals.** There used to be a `Machine.total_hours` counter kept in sync by `MachineUsage.save()`/`delete()` with `F()` updates and a `select_for_update()`, and with it a standing rule against `bulk_create`/`queryset.update()`/`queryset.delete()` and against letting a `WorkOrder` cascade onto a usage row. **No page read it** — and it counted unapproved jobs, so it never agreed with Stroje anyway — so the column and both model methods were dropped. `MachineUsage` is an ordinary model now, and `_write_job_rows` bulk-deletes its rows. **Every row on a job cascades when the job is deleted** — line items and fill-ups included — so `job_delete` is a plain `work_order.delete()`, the same delete the admin performs. `AdminJobDeleteTests` covers the admin's delete page and „delete selected" action. `_machine_summary` annotates `Sum('usages__hours')` **and `Sum('usages__tons')`** (and `_refuel_summary` the litres beside them) over the rows the page's own filter allows (`usages__in=usages.values('pk')`), so the totals and the detail rows below them can never disagree, and both respect the review status. **Every active machine is listed**, not just the ones with rows in range — with no filter that is the whole fleet, and under a date filter a machine sitting at `0 h` answers "what ran last week" — except that naming a machine in the filter narrows the table to it. An invalid filter returns `Machine.objects.none()`, the same rule the rows follow.

**Stroje's second pair of cards is „Tankování" and „Detail tankování", under the same filter.** `_filtered_machine_refuels` applies `MachineFilterForm` unchanged — its three lookups (`machine`, `work_order__created_by`, `work_order__performed_on`) read identically on `MachineRefuel`, so the two halves of the page cannot disagree about what the filter means — and `_refuel_summary` annotates `Sum('refuels__litres')` and `Count('refuels')` over the rows the filter allows (`refuels__in=refuels.values('pk')`), repeating `_machine_summary`'s two rules: every active machine is listed, and naming one narrows the card to it. It stays a **queryset** where `_machine_summary` has to be a list, because there is no per-row Python rule here: the zeros are real zeros (`Coalesce` to `0`, no „—"), so `machine_refuel_export` needs no `_csv_number` blank either. The card's „Celkem" is one `aggregate` over the same rows. **Stroje is the one page with two paginated tables**, so each carries its own page parameter: `_paginated(request, rows, param)` returns `page_obj`, the `querystring` its links carry and `page_param`, dropping only that table's own parameter so the filters and the other table's page survive; `_list_page_context` is that helper plus `date_presets`, `_pagination.html` reads `page_param` instead of writing `page` itself, and `_date_preset_links` drops both (a new range starts at page one in either table). One shared `page` would have moved both tables at once and made one of the two links lie. `MachineRefuelReportTests` covers the card, the filter, the two paginators and the export.

`_time_worked_summary` in `workorders/reports.py` sums `WorkerHours.hours` per user over the scoped work orders. The view re-queries by `pk__in` into `scoped` before aggregating, because the collaborator filters join the M2M and would otherwise multiply the `Sum`. Two separate scoping steps, both needed: the *queryset* is narrowed by `participation_filter` (created-by or collaborator) so a worker only sees jobs they took part in, and then the summary **rows** are filtered again to `row['user'] == request.user` — without that second pass a collaborated job would put the creator's hours on a worker's screen.

All pages are mobile-first templates under `templates/workorders/`. **The Zpracování form's body is one partial, `_job_form_fields.html`** — the job's own fields plus the four formset sections — included by both `transform_form.html` and `job_edit.html` inside each page's own `<form>`, so a field added to a formset row cannot land on one page and be forgotten on the other; only the heading, the primary submit button and the *Zpět bez uložení* link stay with the caller. It carries no `<form>` tag and no `{% csrf_token %}`. **The row buttons do live in the partial**, a „+ další řádek" / „− odebrat řádek" pair per section, because they belong to the rows they resize. The four sections render from one loop over `sections`, which `_job_context` puts in the context alongside each formset under its own name. **It also renders every error either page can produce, which is a rule and not a nicety**: nothing is written unless all five forms validate, so an error with nowhere to render is a submission that vanishes — the page comes back carrying what was typed, with no message anywhere, looking exactly as if the button had not been pressed. Row errors go through `templates/workorders/_row_errors.html` (non-field errors *and* a labelled line per field error, since a row's selects have no visible labels of their own); each section renders its `non_form_errors`; the job form renders `location`, `description`, `notes`, `author` and non-field errors beside the two that were always there. Relatedly, `RowForm.clean()` — the base of all three row forms, which also holds their shared all-or-nothing rule and the `keep` wiring — returns early when `self.errors` is non-empty — a field that failed validation is absent from `cleaned_data`, which reads exactly like a half-filled row, so „Vyplňte materiál i množství…" would otherwise print *over* the real complaint and tell the reader to do what they had already done. Two things let one partial serve both pages: „Zapsat za" sits behind `{% if order_form.author %}`, false on `job_edit` because that view builds `WorkOrderForm` without a `user` so the field is never added; and the hours label is read off the form instead of being written into the markup, because `job_edit` overrides it to „Hodiny – <author>" (a manager correcting someone else's job is looking at neither „Moje hodiny" nor a bare „Odpracované hodiny"), set after both branches since an invalid POST re-renders too. **A section is resized two ways, and the round-trip is the one that must always work.** Each of the four sections carries two submit buttons, „+ další řádek" named `add_<prefix>` and „− odebrat řádek" named `remove_<prefix>` (`add_workers`, `remove_consumed` and so on — the sections are `JOB_SECTIONS` in `workorders/forms.py`, a tuple of `JobSection` — prefix, context name, title, row form and the section's `UniqueChoiceFormSet` subclass — which `_job_form_fields.html` loops over and which is the only place a fifth section would need adding). `_job_forms` — the one form builder both `transform_create` and `job_edit` call — checks `_pressed_row_button` ahead of the submission branch, which returns `(prefix, delta)`, and then rebuilds every form on the page from the raw POST with that section one row bigger or smaller; any other POST comes back bound, and `_valid_job_rows` runs the validations and the mass balance before either view writes. **Removing takes the *last* row — the exact one adding appends**, so the two buttons undo each other; anything cleverer (drop the last *empty* row, say) would make the button hard to predict by looking at it. **No section can fall below `MIN_ROWS_PER_SECTION` (1)**: `_resized_section` applies that floor to every section on every rebuild, not just the one whose button was pressed, so neither a repeated „− odebrat řádek" nor a hand-edited `TOTAL_FORMS` can leave a bare heading with no row under it. The template additionally hides „− odebrat řádek" on a section already down to one row — presentation only, since the view holds the floor either way; it is rendered **carrying the `hidden` attribute rather than left out**, because `job_rows.js` toggles it back, which is what makes the `button[hidden]` CSS rule above load-bearing. **The rebuild is unbound, and that is the whole point**: asking for a row is not submitting, so the page has to come back carrying what was typed and complaining about nothing — a bound rebuild would put „Toto pole je vyžadováno." over the hours box of somebody who has not reached it yet, and the mass balance would object to a form still being filled in. Raw POST strings round-trip through an unbound widget without help: a pk re-selects its option, and a date string reaches `<input type="date">` unchanged rather than through the `cs` `DATE_INPUT_FORMATS` that would render it `05.09.2026` and blank the box — the same trap `WorkOrderForm.performed_on` carries an explicit `format` for. Three things are easy to break here: both buttons need `formnovalidate`, or the browser refuses to submit a half-filled form and they silently do nothing; `job_row_formset` builds a class per call because `extra` is a class attribute, so a formset sized to its caller needs a class of its own rather than a constructor argument — and it builds every formset on the page, so there are no module-level formset classes; and because a browser submits a form through its **first** submit button when Enter is pressed, both callers open their `<form>` with an off-screen decoy submit (`.visually-hidden`, no `name`, `tabindex="-1"`) so Enter still saves instead of adding a collaborator row. `TOTAL_FORMS` is read straight out of the POST on this path, so it is untrusted: it is parsed defensively and clamped between `MIN_ROWS_PER_SECTION` and `MAX_ROWS_PER_SECTION`. `RowButtonTests` in `workorders/tests.py` covers all of it. **`static/js/job_rows.js` then does the same resize in the DOM, and everything above stays true when it does not run** (see the Tech stack section for why that is a constraint rather than a nicety). It **builds no markup**: each section renders Django's own `formset.empty_form` into a `<template>`, and a new row is that template with `__prefix__` swapped for the next index plus a `TOTAL_FORMS` increment — so the widgets, option lists and `empty_label`s still come from `forms.py`. `empty_form` is built from the formset's `form_kwargs`, which is what gets the workers template row the right `collaborator_queryset(user, viewer)` pair and the catalog rows their `keep`; it is deliberately *not* narrowed by `_hide_taken_choices` (which only touches `formset.forms`), so it carries the whole catalog and the script hides from it live. Four agreements it has to keep with the server, each with a test: **removing takes the last row** so indices stay contiguous `0..TOTAL_FORMS-1`; the floor and the cap are **rendered, not restated** — `_job_context` publishes `min_rows`/`max_rows` and each section carries them as `data-min-rows`/`data-max-rows`; a row and its errors are wrapped together in **`.row-block`** so removing the last row takes its messages with it; and the no-duplicates rule is applied by hiding and disabling options only, never by touching what the server validates. `RowTemplateTests` covers that contract — the script's own behaviour is untested and would need a browser runner this project does not have, which is exactly why it is only ever allowed to be an optimisation. Login and password-change are Django's own generic views, wired in `config/urls.py` with the Czech `CzechAuthenticationForm`/`CzechPasswordChangeForm` from `accounts/forms.py` and templates under `templates/registration/` — `accounts` has no `views.py` and no `urls.py`.

The bottom nav is hardcoded in `templates/base.html` and needs a new page's entry added by hand. Workers see Zpracování / Hodiny; **Přehled, Stroje and Materiál are inside `{% if user.is_manager_or_admin %}`**, which puts a manager at five entries — `nav.bottom a` is `flex: 1` at `0.72rem` with `overflow-wrap: break-word`, so they fit but keep a new label short (hence „Materiál", not „Materiály"). The `/jobs/` review views **and both `machine_dashboard` and `material_dashboard`** are gated with `@role_required(User.Role.MANAGER, User.Role.ADMIN)`, so a worker who types one of those URLs gets a 403. Hiding a link is not access control; if a page is meant to be manager-only, gate the view too. Stroje was nav-only for a while and is not any more. **The gate replaced its worker scoping rather than layering on top of it**: `_filtered_machine_usages` no longer filters by `participation_filter`, and `MachineFilterForm` lost its `__init__` (and its `user` kwarg) along with the `del self.fields['created_by']`, because nobody who can reach the view is scoped. Everyone past the decorator sees the whole depot. `MachineUsageDetailTests` asserts the 403 instead of the scoping it used to cover. Relaxing the gate means writing both halves back.

Page-scoped CSS is keyed off the URL name: `base.html` renders `<body class="page-{{ request.resolver_match.url_name }}">`. So **renaming a URL name silently drops that page's styling** — grep `static/css/app.css` for `.page-` before touching `urlpatterns`. There is no test covering the pairing. (No `.page-` rule survives the stock removal, so the file is currently empty of them.)

Two cross-cutting patterns that every list view follows; match them in new views rather than inventing a variant (`job_dashboard` follows the second one; the first does not apply to it, since the whole view is manager-only and there is nothing to scope):

- **Worker scoping is enforced in the view queryset, not by hiding fields.** `time_worked` filters to `Q(created_by=user) | Q(collaborators=user)` for non-manager/admin users, *and separately* `del`s the `worker` field in `TimeWorkedFilterForm.__init__`. The `del` is only cosmetic — the queryset filter is what makes `?worker=<someone else>` a no-op, and `test_worker_cannot_bypass_restriction_via_worker_param` asserts it. **`time_worked` is the only page this still applies to**: it is the one filtered list a worker can open. `machine_dashboard` used to follow it and no longer does — see the role gate above. Follow the pattern in any new worker-reachable list view, and don't add it to a `role_required` one, where it is unreachable by construction.
- **Every filter form gets the quick date ranges.** `_date_preset_links(request)` in `workorders/reports.py` builds them from `DATE_PRESETS` (Vše / posledních 7 dní / posledních 30 dní / minulý měsíc); all four filtered pages get it from `_list_page_context(request, rows)`, the helper that returns the three keys a filtered list needs — `page_obj`, `querystring` (every parameter but `page`, so a page link carries the filters) and `date_presets` — and the row itself is `templates/workorders/_date_presets.html`, included by `_filter_card.html` — the invalid-filter warning, the presets and the form, which is what each list page includes. Page links are `_pagination.html`. They are **plain links that set `date_from`/`date_to` in the querystring**, not a form field — one tap on a phone, no JS, and because the form is bound afterwards the chosen range shows up in the two date inputs. Each link copies the rest of `request.GET` (so the machine or worker already picked survives) and drops `page` (a new range starts at page one). Dates go in as ISO, which `cs` parses because Django appends `%Y-%m-%d` to every locale's `DATE_INPUT_FORMATS`. The spans include today, so „posledních 7 dní" is today plus the six before it; „Vše" removes both parameters and is the way back out of a range on a phone, where emptying a date input by hand is fiddly. A new filtered page needs the context keys *and* the `_filter_card.html` / `_pagination.html` includes — neither half works alone; `**_list_page_context(request, rows)` covers the context half, and taking only part of it is the failure that is hard to spot (the filter vanishes on page two).
- **An invalid filter form returns `.none()`, never the unfiltered queryset.** Silently ignoring a bad filter would hand back everything under a "these are your filtered results" heading. An *unbound* form (no querystring at all) does show everything — the distinction is `form.is_bound`, checked before `form.is_valid()`. **Both halves live in `DateRangeFilterForm.filter()`**, and no view writes them out: a filter form declares `lookups` (field name → ORM lookup string, or a callable returning a `Q`, which is how `TimeWorkedFilterForm` applies `participation_filter`) and `date_lookup` (`performed_on`, or `work_order__performed_on` for row-level pages), and the view calls `form.filter(queryset)`. A new filter form gets the rule for free by subclassing.

Superusers bypass role checks in three places — `role_required`, `User.is_manager_or_admin` and `User.has_admin_access` — because `createsuperuser` never sets a `role`, so a bootstrap admin would otherwise default to `WORKER` and be locked out of the app it administers, the admin gate included.

User-facing copy (auth forms in `accounts/forms.py`, form labels/`empty_label`s in `workorders/forms.py`, the `RETIRE_HELP_TEXT` blocks in `materials/models.py` and `machines/models.py`, model `TextChoices` labels, etc.) is written in Czech for depot workers by **hardcoding Czech strings/labels directly** rather than going through Django's i18n framework — keep new user-facing text in the same style rather than introducing `{% trans %}`/`gettext` half-way.

`LANGUAGE_CODE = 'cs'` and `TIME_ZONE = 'Europe/Prague'` cover the parts the app doesn't write itself. The language setting is what makes **Django's own** strings Czech — admin chrome, `contrib.auth`, and form validation errors (`Toto pole je vyžadováno.`, `Zadejte číslo.`) — using the `.mo` catalogs Django ships. `LocaleMiddleware` is deliberately *not* installed, so the language is fixed rather than negotiated per-request from `Accept-Language`. The two mechanisms are complementary: the setting handles framework strings, hardcoding handles app copy.

Consequences of the locale worth knowing before you touch numbers or dates:

- **Template output of numbers is localised** — `{{ row.hours }}` renders `12,50`, not `12.50`. Tests that assert on rendered quantities must use the comma. `|floatformat:N` localises too, so `{{ machine.filtered_hours|floatformat:1 }}` renders `6,0 h`. Form inputs are *not* localised (fields default to `localize=False`), so `NumberInput` still renders and accepts `value="12.50"` with a dot, and a comma typed into a `DecimalField` is rejected with `Zadejte číslo.` Leave it that way — setting `localize=True` would downgrade the widget from `<input type="number">` to a plain text input and cost mobile users their numeric keypad. **Anything written outside a template has to localise itself**: the summary CSV exports call `number_format(value, decimal_pos=N)` per cell, which is also why they are `;`-delimited — a comma decimal and a comma delimiter cannot share a file.
- **Date input still round-trips.** Czech `DATE_INPUT_FORMATS` is `%d.%m.%Y`-first and does not list ISO, but Django appends `%Y-%m-%d` to every locale's list, so the `<input type="date">` widgets on the filters parse normally. Bound forms re-render the raw submitted string, so filters survive pagination. **The trap is an *unbound* date field with a python-`date` `initial`**: it renders as `14.08.2026`, which an `<input type="date">` rejects as invalid and shows blank. `WorkOrderForm.performed_on` is exactly that — pre-filled with today, and pre-filled with the job's own date on `job_edit` — so its widget passes `format='%Y-%m-%d'` explicitly. Any new pre-filled date field needs the same.
- **Every `ModelChoiceField` needs an explicit `empty_label`.** Django 6 defaults it to `- Select an option -`, which is *not* a translatable string — it renders English even under `cs`, so it cannot be fixed by the locale. The transform formset rows in `workorders/forms.py` use the bare noun instead — `Materiál` / `Stroj` / `Pracovník` — because each row renders the selects side by side with no room for a visible label, so the empty option *is* the label (and for the same reason `hours` on those rows carries a placeholder instead). Filter forms (`MachineFilterForm`, `MaterialFilterForm`, `TimeWorkedFilterForm`, `JobFilterForm` — all four subclass `DateRangeFilterForm`, which carries the `date_from`/`date_to` pair and the „od ≤ do" check, so each declares only its own fields plus a `field_order` to keep the dates rendering last) use an "all" phrasing, since a blank there means "don't filter": `Všechny stroje`, `Všechny materiály`, `Všichni pracovníci`, `Všichni uživatelé`. `EmptyLabelTests` in `workorders/tests.py` fails if a new field forgets. `ModelMultipleChoiceField` (e.g. `collaborators`) has no blank option and needs nothing.
- **Time is 24-hour everywhere the app renders it** — templates use `H:i` and Czech `TIME_FORMAT` is `G:i`. The app no longer renders a `<input type="datetime-local">` anywhere; that widget was the one place the browser, not the app, picked the format (an English-configured phone showed AM/PM regardless of `lang="cs"`), and it went with the Příjem/Výdej back-dating checkbox. If you reintroduce one, that caveat comes back with it.
- **Keep explicit date formats in templates.** Timestamps use `|date:"Y-m-d H:i"`, which is locale-independent; a bare `{{ ... }}` on a date would render as `14. srpna 2026` instead.
- **`USE_TZ` stays on, so the DB still stores UTC** — `TIME_ZONE` only affects rendering. No filter depends on it any more: the date filters compare `WorkOrder.performed_on`, which is a `DateField` with no time and no zone, so a job recorded at 00:30 local cannot land on the previous UTC day the way a `created_at__date` lookup could. Python code does *not* auto-localise, so anything formatting a datetime outside a template needs `timezone.localtime()` explicitly. Nothing does today — the summary CSV exports format decimals (through `number_format`) and one `localdate()` in a filename, and neither is a datetime.

**The Django admin is fully Czech too, via three separate mechanisms** — a new model or admin needs all three or it will show English in one place:

1. **App labels** — `verbose_name` on each `AppConfig` (`Materiály`, `Stroje`, `Lokace`, `Zakázky`, `Uživatelé`), which is what the admin index groups by. Those five are the whole index: **`auth.Group` is unregistered** in `accounts/admin.py`, which also takes Django's own `Autentizace a autorizace` section with it. Permissions play no part in this app — access is `role` + `role_required`, and every account that can reach the admin is a superuser, which bypasses permission checks — so a group could only ever be a no-op mistaken for access control. `CustomUserAdmin` had already dropped `groups`/`user_permissions` from its `fieldsets`; this is the last trace. Nothing is deleted, and re-registering restores it.
2. **Model and field names** — Czech `verbose_name`/`verbose_name_plural` in every `Meta`, and an explicit lowercase `verbose_name` on every field (Django capitalises it where needed). Adding one is a migration: `makemigrations` emits `AlterField` for a pure label change, and CI fails without it.
3. **`LOCALE_PATHS` → `locale/cs/LC_MESSAGES/django.po`** for the handful of *Django's own* strings whose `cs` translation Django doesn't ship — `- Select an option -`, the delete-confirmation sentence, the date-hierarchy label (rendered by `WorkOrderAdmin`, the one admin with a `date_hierarchy`), the two screen-reader-only `Search %(name)s` / `Pagination %(name)s` headings. These are not fixable by `LANGUAGE_CODE`, because the msgid simply isn't in the catalogs Django installs. This is the one place the project *does* use the i18n framework, and it holds Django msgids only — app copy stays hardcoded.

The catalog is read from the **compiled `.mo`, and both files are committed**; editing the `.po` alone changes nothing at runtime. Recompile with `python manage.py compilemessages -l cs --ignore=.venv` — without the `--ignore` it walks into the virtualenv and recompiles every catalog Django ships. `AdminCzechTests` in `accounts/tests.py` fails if the `.mo` is missing or stale, so CI catches a forgotten recompile.

What this *can't* reach: `filter_horizontal`. Its widget builds labels in JavaScript from the `djangojs` catalog, and the admin's `jsi18n` view loads only `django.contrib.admin`'s own locale dirs — `LOCALE_PATHS` is ignored there, so three untranslated strings ("Choose %s by selecting them…") would render English. `WorkOrderAdmin` therefore uses the plain multi-select for `collaborators`; don't reintroduce `filter_horizontal` without checking that.

Local dev (without Docker), from a virtualenv with `requirements.txt` installed:

```bash
python manage.py runserver
```

```bash
python manage.py makemigrations
python manage.py migrate
```


```bash
python manage.py test
```

Run a single app's tests, or a single test case/method, the same way:

```bash
python manage.py test materials
python manage.py test materials.tests.MaterialModelTests.test_material_str
```

Tests are one `tests.py` per app, plain `django.test.TestCase`, no pytest and no mocking — almost everything drives a real view through `self.client` and asserts on both `response.context` and the resulting rows. Postgres is required; there is no SQLite fallback, and no separate test settings module, so a change to `config/settings.py` (locale included) is a change to how the suite behaves.

`workorders/tests.py` is where the app is actually covered, `StockMovement`'s model-level tests included. **Migrations were reset** to one `0001_initial` per app while production held no data (the `inventory` app went with them); once real rows exist, model changes get ordinary migrations on top. `accounts/views.py` and `materials/views.py` are gone too: both held nothing but `# Create your views here.`, and neither app — nor `machines`, which never had one — serves a page (auth uses Django's own generic views, wired in `config/urls.py`).

The suite has **no `TransactionTestCase`, and needs none**: there is no concurrent write path left. `StockLockConcurrencyTests` went with the stock pages, and the last `select_for_update()` went with `Machine.total_hours`. Every write is now a plain insert or delete whose outcome does not depend on what another request is doing. Add a counter or any other read-modify-write and that changes — a plain `TestCase` wraps the whole test in one transaction and hides the interleaving, so such a test has to be a `TransactionTestCase`.

Seed the material catalog, machinery, and employee accounts from CSV (idempotent — safe to re-run; matches the `.env`/`.env.example` pattern, real files are gitignored):

```bash
cp seed_data/materials.example.csv seed_data/materials.csv
cp seed_data/machines.example.csv seed_data/machines.csv
cp seed_data/users.example.csv seed_data/users.csv
# edit those three files with real data, then:
python manage.py seed_data
```

`machines.csv` takes `name,hourly_rate,rate_per_ton` — a machine stores no hours to seed; Stroje sums them from the approved usage rows on every render. `materials.csv` takes `sku,name`. **A material carries nothing else** — `category` and `unit_of_measure` were both removed. **Every quantity in the app is tonnes**, implicitly: there is no unit field to read, so the `t` in the form prompt („Množství (t)"), the job detail table and `StockMovement.__str__` is hardcoded. `csv.DictReader` ignores columns the command does not read, so an older CSV that still carries the retired ones keeps working.

The optional `hourly_rate` and `rate_per_ton` columns are only written when the CSV actually carries a value for that row: omitting the column, or leaving the cell blank, **preserves** whatever is already in the database, so re-seeding never clobbers a rate someone set by hand in the admin. New records still fall back to the model default (`NULL` for both). Clearing a value back to empty is an admin action, not a CSV one.

New users get a random temporary password printed to the console (share it securely); only `ADMIN`-role users get Django admin access — both `is_staff` (to log in) and `is_superuser` (to actually see/edit anything there; `is_staff` alone gets an empty "you don't have permission" admin index). Managers do not get admin access at all — what distinguishes them in the app is `is_manager_or_admin`: the Stroje nav entry, and an unrestricted view of everyone's hours and machine usage rather than just their own.

CI (`.github/workflows/ci.yml`) runs three jobs on every push/PR. **`lint`**: `ruff check`, `ruff format --check` (must pass, not just run) and `shellcheck scripts/*.sh`. **`test`**: `manage.py check`, then `manage.py makemigrations --check --dry-run`, then `manage.py test` — that middle step means **a model change without its migration file fails CI even if every test passes**, so run `makemigrations` and commit the result alongside any `models.py` edit. **`docker-build`** (the id is kept for branch protection; it does far more than build) runs `scripts/smoke_prod_stack.sh`, which brings up `docker-compose.prod.yml` — db, web *and* Caddy — on a throwaway project with an `.env.production` generated from `.env.production.example`, and asserts: compose and `caddy validate` accept their files, the login page links a **hashed** `app.css` that is served, `check --deploy` reports exactly `W021`, HTTP redirects to HTTPS, HTTPS answers 200 with HSTS (a 301 means Django stopped seeing HTTPS — `X-Forwarded-Proto`/`SECURE_PROXY_SSL_HEADER`), and a login POST carrying `Origin:` gets a 302 (a 403 is the CSRF origin check). **It does not catch a removed `FORWARDED_ALLOW_IPS` or an empty `CSRF_TRUSTED_ORIGINS`, and that was verified, not assumed**: with each removed in turn, the whole script still passed. Gunicorn 26.2 still forwards `X-Forwarded-Proto` to Django from an untrusted peer (the allow-list only gates its own `wsgi.url_scheme`), and Django's origin check accepts `https://<own host>` once it sees HTTPS. The two Deployment bullets below that call those settings load-bearing predate this finding. So the template's values are under test: **an edit to `.env.production.example` that adds a deploy warning fails CI**. The script writes `.env.production` into the checkout it runs in and refuses to start if one exists — run it locally only in a clean worktree, never on the server. **Both Python jobs pin 3.14 to match the `Dockerfile`**; Dependabot bumps the `Dockerfile` alone, so a new minor has to be copied into `ci.yml` by hand. Ruff's `target-version` stays `py312` deliberately (see `pyproject.toml`). Both triggers carry a `paths-ignore` list, and it is **`'**.md'` and nothing else** — a commit touching only Markdown runs **no jobs at all**, so don't wait for a green check on such a push and don't take one as evidence the code still builds. Everything else, dotfiles and `.github/` included, triggers the full pipeline. Dependabot (`.github/dependabot.yml`) opens weekly update PRs for pip, the `Dockerfile` base image, and the Actions themselves — not for the images named in the compose files.

**Deploys are `.github/workflows/deploy.yml`, manual only** (`workflow_dispatch`, main only, `concurrency` so two never overlap). It refuses unless CI passed for the code: it finds the newest *push* run of `ci.yml` on main that succeeded and requires everything between that commit and the one being deployed to be `*.md` — the only way to deploy past the Markdown-only commits CI never runs on. Then it SSHes to the server and sends **only the commit hash**; the key is restricted in `authorized_keys` with `command="…/scripts/deploy.sh",restrict`, so it can run nothing else, and `deploy.sh` reads the hash from `SSH_ORIGINAL_COMMAND` and accepts exactly 40 hex characters. Secrets (`DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`, `DEPLOY_HOST`, `DEPLOY_USER`) and the `APP_DOMAIN` variable live on the GitHub **`production` environment**, which must be restricted to `main` — repository-level secrets would be readable by a workflow pushed on any branch. Setup is "Automated deploys" in `DEPLOYMENT.md`.

## Deployment

**The deployment is a public VPS behind the company domain, over HTTPS.** It used to be LAN-only, reached by IP over plain HTTP; anything still describing it that way is stale. [DEPLOYMENT.md](docs/deployment/DEPLOYMENT.md) is the runbook you follow on the server, [DEPLOYMENT_PLAN_PUBLIC.md](docs/deployment/DEPLOYMENT_PLAN_PUBLIC.md) is why it looks like this, and [DEPLOYMENT_PLAN.md](docs/deployment/DEPLOYMENT_PLAN.md) is the superseded LAN plan — still the authority on the image, static files, seeding, collation and backups, which did not change. Everything in the repo is ready; only the on-server steps remain.

**There are two compose files and they are not interchangeable.** `docker-compose.yml` is development only (`runserver`, `DEBUG=True`, DB port published to the host, manifest storage turned back off) and **must never be brought up on the server** — on a VPS, a published Postgres port is a Postgres on the internet. `docker-compose.prod.yml` is three services: `db` (unpublished), `web` (gunicorn from the baked image, also unpublished) and `proxy` (Caddy, owning 80/443 and obtaining its own Let's Encrypt certificate from the nine-line `Caddyfile`), all `restart: unless-stopped` with log rotation.

**Going public was almost entirely configuration** — no models of this project's own, no views, no URL changes. There are two exceptions. Login rate limiting (see below) added a dependency, a Czech lockout template and a test class, and brings `django-axes`' own two models with it: **that change needs `migrate`.** The `/admin/` gate (`AdminSessionRequiredMiddleware`, see the `accounts` bullet in Architecture) added a middleware, a `User` property and a test class — no dependency, no model, no migration. **Refuelling since then added `MachineRefuel`, and job locations the `locations` app and `WorkOrder.location`, so both changes need `migrate` too**; `scripts/deploy.sh` runs it from the new image before the swap, so an ordinary deploy covers it. **After deploying locations, create at least one in the admin before anyone records a job** — the field is required on every work job, so an empty catalog makes the Zpracování form impossible to submit (fuel-only jobs excepted).

Eight things about the prod setup that are easy to break:

- **Every command against it needs `--env-file .env.production`.** A service's `env_file:` key populates the *container's* environment and does **not** feed the `${...}` interpolation in the compose file itself, which reads only the shell environment and the project's default `.env`. Without the flag the published port and the DB credentials expand empty — the `:?` guards on `db` turn that into a named error rather than a silent misconfiguration. Note the guards only fire when nothing else supplies the variable: a stray `.env` in the directory would quietly hand the prod stack the *dev* credentials.
- **The project name is `materialinventory-prod`, deliberately.** Compose derives a project name from the directory, so the bare name would collide with the dev file in the same checkout — same `db_data` volume, and the runbook's `down -v` would destroy the development database.
- **`POSTGRES_INITDB_ARGS` sets an ICU `cs-CZ` locale, and it is read only when the volume is empty.** A default `postgres:16-alpine` cluster sorts in byte order, putting `Š` after `Z`; both catalogs order by name, so that is visible in every material dropdown and in the Materiál table. It cannot be changed on an existing cluster without a dump/restore, which is why runbook step 8 checks it before `migrate`. The dev file passes the same argument, but an already-created dev volume keeps byte order.
- **Neither `db` nor `web` publishes a host port, and that is load-bearing.** Docker's published ports are DNAT rules that sit *ahead* of `ufw`, so on a VPS "published" means published to the internet and the host firewall does not contain it. `web` gets `expose: 8000` and is reachable only by the proxy. This is what replaced the LAN file's `APP_BIND_IP`/`APP_PORT` pair, both of which are **gone** — there is no longer a port to bind or choose. It is also what makes `SECURE_PROXY_SSL_HEADER` safe to set unconditionally in `config/settings.py`: that setting tells Django to trust `X-Forwarded-Proto`, which Caddy overwrites on every request but anything reaching gunicorn directly could forge. **Re-adding a `ports:` line to `web` breaks that in the same edit**, and also invalidates the next bullet.
- **`FORWARDED_ALLOW_IPS: "*"` on `web` is not sloppiness, and removing it causes an infinite redirect loop.** Gunicorn discards `X-Forwarded-*` from any peer not in that list and defaults to `127.0.0.1` — which the proxy is not, being a separate container with its own Compose-network address. At the default: the header never reaches Django → `SECURE_PROXY_SSL_HEADER` never fires → `request.is_secure()` stays `False` → `SECURE_SSL_REDIRECT` redirects an already-HTTPS request to HTTPS, forever. The symptom points at the proxy; the fix is not in the proxy.
- **The HTTPS settings all default to off, for the same reason `STATICFILES_BACKEND` does.** `SECURE_SSL_REDIRECT`, `SECURE_COOKIES` (which drives both cookie flags) and the three HSTS settings read from the environment with off-by-default values, because the test runner forces `DEBUG=False` and a hardcoded `SECURE_SSL_REDIRECT = True` would turn every `self.client.get()` in the suite into a 301. Production opts in via `.env.production`. `SECURE_HSTS_PRELOAD` stays off deliberately, so `check --deploy` reports **exactly one** warning (`W021`) — runbook step 12 states that count. And **`CSRF_TRUSTED_ORIGINS` is now required**, with the scheme: Caddy terminates TLS and talks HTTP to Django, so without it every POST fails 403 "Origin checking failed" while every page still loads — the single most misleading failure in this deployment.
- **`down -v` is no longer a safe instruction.** There are three volumes now, and `caddy_data` holds the certificate and the ACME account key. Destroying it forces a fresh issue against Let's Encrypt's limit of **5 certificates per exact hostname per week**; do it a few times while debugging and the site has no certificate and no way to get one. Both the collation fix and the Postgres upgrade in the runbook name `materialinventory-prod_db_data` explicitly instead.
- **The one bind-mount for the app is `./seed_data:/app/seed_data:ro`.** `.dockerignore` keeps the real CSVs out of the image on purpose, and without the mount `seed_data` prints `not found, skipping.` and exits 0 with an empty catalog. The proxy adds one more, `./Caddyfile:/etc/caddy/Caddyfile:ro`, deliberately not baked into the image so it can be edited on the server without a rebuild.

**Login rate limiting is `django-axes`, and it locks the *account*, not the address.** Django ships no brute-force protection and the LAN perimeter used to stand in for it, so this is one of the two things going public genuinely required in code (the other is the `/admin/` gate). `AXES_LOCKOUT_PARAMETERS = ['username']`, five failures, a 30-minute cool-off, cleared by a successful login. **The default (`['ip_address']`) would have been actively harmful**: the depot reaches the app through one office NAT address, and behind the proxy every request axes has not been told about looks like it came from the proxy container — so one worker mistyping their password would lock out everybody. The cost of the choice is that an attacker gets five guesses per account per cool-off from as many addresses as they like, which is the cheaper of the two failure modes. Axes disagrees and says so as `axes.W006` on every `check`/`migrate`/`test`; it is answered in `SILENCED_SYSTEM_CHECKS` with the reasoning, deliberately rather than by ignoring it, because `check --deploy` is supposed to come back with exactly one known warning. Four more things about it: **it adds two models, so `migrate` is required** — pulling this change without it gives `relation "axes_accessattempt" does not exist` on the first login *or logout*; `AXES_ENABLE_ADMIN = False` because axes ships catalogs for ar/de/fa/fr/id/pl/ru/tr and **no Czech**, so its section would be the only English in the admin (`manage.py axes_list_attempts` reads the log instead, and `AdminIndexTests` asserts the section stays out); the lockout page is `templates/registration/lockout.html`, Czech and hardcoded like all app copy, and it **quotes the 30 minutes in prose**, so `AXES_COOLOFF_TIME` and the template change together; and `BEHIND_PROXY` (off by default, `True` in `.env.production`) is what makes the recorded IP the real client rather than the proxy — an audit-trail setting, not an availability one, since locking is by username. **`AxesStandaloneBackend` goes first in `AUTHENTICATION_BACKENDS` and deliberately defines no `get_user`**, which is what keeps the suite working: `Client.force_login()` picks the first backend that has one, so all ~130 `force_login` calls resolve to `ModelBackend`. `Client.login()` would raise — it calls `authenticate()` with no request — and there is not one in the project. Keep it that way. `LoginRateLimitTests` in `accounts/tests.py` covers the policy.

**One security gap that the LAN perimeter used to cover and still nothing does: `seed_data` prints a random temporary password per user**, and any that were handed out informally are now internet-facing credentials. It is not a bug introduced by going public — it is something the network was silently answering — and it is stated at the top of [DEPLOYMENT.md](docs/deployment/DEPLOYMENT.md); don't quietly close it without updating both files. **The second gap, `/admin/` on the open internet, is closed in the app** by `AdminSessionRequiredMiddleware` (see the `accounts` bullet in Architecture): the admin is a 404 to anyone not already logged in as an admin, so it is gone from the internet's view without a VPN or an IP list to maintain. The `Caddyfile` keeps its commented source-IP `route` block as an optional second layer — it is now belt-and-braces rather than the only answer, and a VPN still is the thorough one. Relatedly, **everything under `static/` is now unauthenticated to the internet** rather than to the depot — no new hole (`static/xlsx/` is already excluded from `.gitignore` and `.dockerignore`) but a larger consequence for getting it wrong.

`config/settings.py` carries a `LOGGING` block for the same class of reason: with `DEBUG=False`, no `ADMINS` and no mail backend, Django's default records an unhandled 500 **nowhere**, and gunicorn only sees an ordinary response. It logs `django.request` to stdout at `ERROR` — `ERROR` and not `WARNING`, because 4xx are logged at `WARNING` and the suite asserts a great many 403s.

`scripts/backup_db.sh` is `pg_dump | gzip` into `backups/` (gitignored) with 30-day retention, installed as a cron entry by hand. **`scripts/deploy.sh` is the one update procedure**, run by hand (`./scripts/deploy.sh`, deploying `origin/main`) or by the deploy workflow: fetch → refuse anything not on `origin/main`, anything *older* than `HEAD` (code rolls back, the schema does not — a rollback is a person's decision) or a checkout with commits of its own → `backup_db.sh` → `git merge --ff-only` → `build web` → `run --rm web migrate` → `up -d`. **The order is deliberate: migrate runs from the new image *before* the swap**, so a failed build or migration leaves the old container serving. Re-running it at the current `HEAD` is not a no-op — it rebuilds, migrates and restarts, which is how a half-finished deploy is finished. `.gitattributes` pins `*.sh` to LF: the repo is edited on Windows and run on Linux, where a CRLF script dies with `/usr/bin/env: bash\r`. Note `.gitignore`'s `.env` line does **not** match `.env.production` — that needed its own entry.

Static files are the part most likely to trip you up, because the correct behaviour differs per environment:

- **`WhiteNoiseMiddleware` is in `MIDDLEWARE` unconditionally**, in every environment including the test run — only the *storage backend* is environment-dependent. So "is whitenoise active?" is the wrong question; the one that matters is which of the two backends is live.
- **The static backend is chosen by `STORAGES['staticfiles']`, driven by the `STATICFILES_BACKEND` env var**, defaulting to plain `StaticFilesStorage`. It is *not* `STATICFILES_STORAGE` — Django removed that setting in 5.1, and it sat in this file being silently ignored until it was migrated. If you ever need to know which backend is really live, check it, don't read the setting: `from django.contrib.staticfiles.storage import staticfiles_storage; type(staticfiles_storage)`.
- **The default is plain storage specifically so the test suite works.** Whitenoise's manifest storage rewrites every `{% static %}` URL to a hashed name looked up in `staticfiles.json`, and raises when there's no manifest — non-strict mode doesn't save you either, since it falls back to hashing the file and that file isn't in `STATIC_ROOT` without a `collectstatic` run. Django's test runner forces `DEBUG=False`, and `DEBUG` is precisely what short-circuits the hashed-URL lookup. So flipping the default to manifest storage makes **every test that renders a template** fail with `ValueError: Missing staticfiles manifest entry`. Don't.
- **Production opts in through the `Dockerfile`,** which sets `ENV STATICFILES_BACKEND=...CompressedManifestStaticFilesStorage` and then runs `collectstatic`. Keep those two together: the `ENV` persists into the running container, so the backend that writes the manifest and the one that reads it can't drift apart. Setting the backend in `.env.production` instead would reintroduce exactly that split.
- **`static/` is source, `staticfiles/` is generated.** `.gitignore` used to ignore the former, which is why `static/img/background.jpg` — referenced by `static/css/app.css`, which every page loads — was missing from the repo for a while. New assets go in `static/` and must be committed.
- **Don't park non-assets under `static/`.** `collectstatic` publishes everything there at an unauthenticated `/static/` URL. `static/xlsx/` holds a working spreadsheet and is excluded in both `.gitignore` and `.dockerignore` for that reason; it would be better off outside `static/` altogether.
- **Only the `docker-build` job covers this.** The test job runs with plain storage and never requests a static URL; `scripts/smoke_prod_stack.sh` runs the built image behind Caddy and fails unless the login page links a hashed `app.css` and serves it. It checks that one file, so a static change that matters beyond the stylesheet is still worth curling by hand.
