# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MaterialInventory records material **processing jobs** — what a transformation consumed and produced, who worked it and for how long, and which machines ran.

**It no longer tracks stock.** Příjem (receipt), Výdej (shipment) and Úprava (adjustment) were removed along with the stock dashboard, movement history and CSV export, `track_stock`, and every balance/sufficiency check. Nothing sums quantities into an on-hand figure and nothing blocks a job for insufficient material. The one quantity rule left is **within** a single job: a transformation's consumed and produced totals must match (see Architecture), which is mass balance across the form being submitted, not a stock level. The name is now historical — don't reintroduce inventory semantics because the repo is called MaterialInventory.

## Tech stack

Django 6, PostgreSQL, server-rendered templates, no separate JS frontend. Depot workers fill out mobile-first web forms; Django's admin serves as the back-office UI for managers.

Three dependencies are installed but **not actually used yet**, so don't assume their patterns are established: `django_htmx` (the htmx script tag is in `base.html`, but no template has an `hx-*` attribute — every page is a plain form POST + redirect), `widget_tweaks` (no template loads it), and `rest_framework` (configured in `REST_FRAMEWORK` for session auth + `IsAuthenticated`, but there are no serializers, viewsets, or API routes). All page CSS is one file, `static/css/app.css`, loaded by `templates/base.html`; no template carries an inline `style=` attribute or a `<style>` block of its own. **Every colour in it is a custom property declared twice** - once in `:root` for light, once again under `@media (prefers-color-scheme: dark)` - so a colour literal written into a rule below those two blocks is a bug: it will be right in one theme and wrong in the other. Dark mode follows the operating system setting and nothing else: no toggle, no stored preference, no JavaScript, and `base.html` carries a `theme-color` meta per scheme whose values must be kept in step with `--chrome-bg` by hand. `ThemeTokenTests` in `workorders/tests.py` reads the stylesheet and fails if the two blocks declare different token sets, if a `var()` names a token nobody declared, or if a literal survives below them. The admin ships its own dark theme, driven by the same media query, so it needs nothing.

## Architecture

Modular monolith, one Django project (`config`) with these apps:

- `accounts` — custom `User` model with a `role` field (`WORKER`/`MANAGER`/`ADMIN`) and an `is_manager_or_admin` property. `accounts/decorators.py::role_required(*roles)` gates privileged views (401/redirect if anonymous, 403 if wrong role).
- `materials` — `Material` catalog (SKU and name only) and `Machine` (name, `is_active`, and two optional reference rates, `hourly_rate` in Kč/hod and `rate_per_ton` in Kč za tunu zpracovaného materiálu — neither is used in any calculation). `materials/management/commands/seed_data.py` bulk-loads materials/machines/users from CSV (see Commands below). **Locations are gone**: the `Location` model, `StockMovement.location`, the form column, the admin entry and `locations.csv` were all removed (migrations `inventory.0006` / `materials.0008`, which drop the column and the table — the recorded values are not recoverable). A job line item now records *what*, not *where*.
- `inventory` — **model only; it has no views, no forms, no URLs and no admin.** `StockMovement` (name kept to avoid a table rename) is one material line item on a job: what it consumed, as a negative quantity, or produced, as a positive one. `movement_type` is `TRANSFORM_CONSUME` or `TRANSFORM_PRODUCE` — nothing else. **A line item has no timestamp of its own** — its date is its job's `performed_on`, and `Meta.ordering = ['id']` keeps a job's rows in the order they were typed. It used to carry `created_at`, `recorded_at` and a `notes` field no form ever wrote; migration `inventory.0007` dropped all three because nothing read them, and deleted the last two rows carrying the retired `RECEIPT`/`SHIPMENT` values — which were also the only movements without a job, so `work_order` stopped being nullable. `MovementType` now describes every row in the table. **`StockMovement` is not registered in the admin**: a line item never exists apart from its job, and `WorkOrderAdmin` already edits the rows as an inline, so registering it as well put a second top-level section in the index — labelled `Zpracování`, like the worker form, and holding one model reachable from Zakázky anyway. Everything about a job is edited in one place. That leaves `inventory` with no model in the admin at all, so its `AppConfig.verbose_name` no longer appears anywhere; it is kept for whenever something is registered again. 
- `workorders` — **the whole app, effectively.** `WorkOrder` groups the `StockMovement` line items from a single transformation job, plus a `collaborators` M2M. One submission also writes one `WorkerHours` row per participant and any number of `MachineUsage` rows (chained machines supported), all in a single `transaction.atomic()` — the three record types are one job and must not land half-written. Formset rows are written exactly as typed; the view no longer combines repeated material rows, because the only reason it did was to stock-check them as a unit. **A job must balance: it needs at least one consumed row and one produced row, and the two sums must be exactly equal** — `transform_create` compares `sum(consumed)` against `sum(produced)` before opening the transaction and re-renders with a Czech `messages.error` if they differ. Totals, not row-by-row: one input is normally crushed into several output fractions. Exact `Decimal` equality, no tolerance, so `5.00` and `5` pass but `5.01` and `5` do not. The form's `quantity` accepts 2 decimal places while `StockMovement.quantity` stores 3 — a form tighter than its model is fine and needs no migration, but it means the tightest mismatch the check can be tested against is `0.01`, not `0.001`. The check has no database state behind it, which is why it sits in the view ahead of the write rather than in a model `clean()`. **A job carries the date it was performed**, `WorkOrder.performed_on`, separate from `created_at` (when it was typed in). `WorkOrderForm.performed_on` is a required date field **pre-filled with today** (`initial=timezone.localdate`), so the common case is already answered and back-dating means editing the box. An empty or future date is a form error, so nothing at all is written. `job_edit` shows the job's own date, not today, so a correction that touches nothing else does not move it. Day only, no time: `<input type="date">` renders the same everywhere, while the `datetime-local` widget the removed Příjem/Výdej forms used let an English phone show AM/PM under `lang="cs"`. **The widget carries an explicit `format='%Y-%m-%d'`** — this is the one form in the app with an unbound date field holding a python `date`, and without it the value renders through the `cs` `DATE_INPUT_FORMATS` as `02.09.2026`, which `<input type="date">` rejects outright and shows as an empty box. Two tests assert the rendered `value=`. Migration `0010` added the column with a `timezone.localdate` default and then back-filled every existing job from `created_at` — before the field existed a job could only be recorded on the day it happened. **Every report keys off it.** The date filters on Hodiny, Stroje and Přehled compare `performed_on` (a `DateField`, so a plain `__gte`/`__lte` — no `__date` lookup and no timezone conversion), every "Provedeno" column shows it, and ordering is `[-performed_on, -created_at]` — on the three lists *and* in `WorkOrder.Meta` (migration `0011`). **Machine-usage rows are dated by their job**, `work_order__performed_on`, not by `MachineUsage.created_at`: `job_edit` deletes and rewrites every row, so a corrected job would otherwise drift to the day it was corrected. The one list still ordered by `-created_at` is `my_jobs` — it is a recency list of *submissions*, and a job just back-dated to last month has to appear at the top of it, which is the whole reason a worker opens it; its date column still shows `performed_on`. `created_at` survives as "when it was typed in" on the job detail page („Zaznamenáno"), the edit and delete pages, and the admin. The totals in that error message go through `django.utils.formats.localize` — an f-string would print `9.5` where the rest of the UI shows `9,5`. Beyond the Transform form there are two read-only views: **Stroje** (`machine_dashboard`) and a per-person time-worked report (`time_worked`). Both are built the same way — one filter driving a summary table and the detail rows it is made of. Stroje sums motohodiny and tonnage per machine (and shows both reference rates), then lists the individual `MachineUsage` rows underneath — plus the review pages described next.

The app is four pages: **Zpracování** (`transform_create`, mounted at `/` and the landing page), **Hodiny** (`time_worked`), **Stroje** (`machine_dashboard`) and **Přehled** (`job_dashboard` at `/jobs/`, with its detail/edit/delete pages). There is no separate machine-history page any more — `machine_usage_history` and its template were folded into Stroje, because the totals and the rows behind them are the same data at two zoom levels and splitting them across two URLs meant filtering twice. `workorders/urls.py` is mounted at the root in `config/urls.py`; `inventory` contributes no URLs at all.

**A job does not count until it is approved.** `WorkOrder` carries `status` (`PENDING`/`APPROVED`), `reviewed_at` and `reviewed_by`. `transform_create` writes a worker's submission as `PENDING`; a manager's or admin's own submission is written `APPROVED` with themselves as reviewer, because there is nobody above them to sign it off. **`time_worked` and `machine_dashboard` both filter to `status=APPROVED`** — a pending job is recorded but invisible in every report, including to its own author, so the submit message tells the worker it is waiting. Migration `0008` back-filled every pre-existing job to `APPROVED` (reviewed_at = created_at, no reviewer): they were counted before the rule existed and must not vanish. The review pages are `job_dashboard` / `job_detail` / `job_edit` / `job_approve` / `job_delete`, all under `/jobs/` and all gated with `@role_required(MANAGER, ADMIN)`. **There are exactly three review actions — schválit, upravit, smazat.** A job is never handed back to its author: there is no `RETURNED` status, no `review_note` and no `job_return` view. Migration `0009` dropped both the status value and the note column, moving any already-returned job back to `PENDING` — it was never approved, so it belongs in the queue. **Only a manager edits a job**, and editing deliberately does *not* approve. What a worker *does* get is `my_jobs`, built by `_my_recent_jobs` and rendered at the **top of Hodiny** (not the Transform form): their own last `MY_JOBS_LIMIT` (5) submissions with a status badge and their own hours (`Sum('worker_hours__hours')` filtered to that user). **That list is the only feedback on the review anyone gets** — a pending job is invisible in every report, so without it there is no telling one awaiting approval from one that never landed; it lives on Hodiny because that is the page the withheld hours are missing from. Three scoping rules, each with a test: it is scoped by `created_by` alone, deliberately *not* by `_participation_filter` (being named on someone else's job is not recording one, and those hours surface in the summary once approved); the `TimeWorkedFilterForm` filters do **not** apply to it, since they scope the approved-hours report and a pending job is exactly what that report cannot show; and `_my_recent_jobs` returns `none()` for a manager or admin, whose Hodiny is the whole depot's report and who have Přehled already. `job_edit` reuses the submission's own helpers (`_collect_rows`, `_balance_error`, `_write_job_rows`), so a correction is mass-balanced exactly like the original, and it writes the rows as the **author** (their hours in „Moje hodiny", `collaborator_queryset` built from the author *and* the editing manager so it excludes the author and not the manager, `created_by=author` on the movements).

**`WorkerHours` (labour) and `MachineUsage` (runtime) are two unrelated numbers** — don't derive one from the other. `WorkerHours` is what a person typed for themselves on the Transform form: the submitter's own hours come from `WorkOrderForm.hours` ("Moje hodiny", required), and each collaborator's from a `WorkerHoursFormSet` row. `MachineUsage.hours` is motohodiny for a machine, and `MachineUsage.tons` is how much material that machine put through on the job — a third independent number. **Tonnage is not part of the mass balance**: chained machines each process the same material, so the machine rows sum to a multiple of the consumed total, and nothing compares them. `tons` is required on any machine row that names a machine, but nullable in the model, because rows written before the column existed have no answer (unknown, not zero); the usage rows render those as a dash, and so do the per-machine totals — `Sum` skips NULLs, so a machine whose usage all predates the column sums to `None` and shows `—` rather than a `0 t` that would read as "processed nothing". The Hodiny tab reports only `WorkerHours`, so its total has no fixed relationship to the motohodiny on Stroje.

**A manager or admin can record a job for someone else.** `WorkOrderForm` grows an `author` field („Zapsat za", `empty_label='Za sebe'`) for them and only for them — a plain worker's form has no such field, so an `author` in their POST is never cleaned and the view has nothing to defend against. When set, the job is written with `created_by=author` and `_write_job_rows(..., author, ...)`, so the hours, the line items and „Moje hodiny" all belong to that person; the field also relabels `hours` to „Odpracované hodiny", since „Moje" would be wrong half the time. **Approval still follows the submitter, not the author**: a manager typing a worker's job in is the reviewer and has just seen the work written down, so it is `APPROVED` with `reviewed_by=<the manager>` and `created_by=<the worker>`. Because the author decides who may be named as a collaborator, `transform_create` settles it before building the `WorkerHoursFormSet` — `order_form.is_valid()` runs first, and an invalid form falls back to the submitter purely so the page can be re-rendered.

`collaborator_queryset(user, viewer=None)` therefore takes **two** people: `user` is the job's author and is excluded from the list (you cannot collaborate with yourself), while `viewer` — whoever is filling the form in — decides how wide the list is. They differ only when a manager acts for someone else, and then the manager's privilege applies: the workers-only restriction exists to stop a *worker* putting hours on a manager, not to stop a manager recording that a manager worked the job. `job_edit` passes the same pair (author + the editing manager). A plain worker recording their own job is unaffected: `viewer` defaults to `user` and the old rule holds.

`collaborators` is **derived**, not entered: `transform_create` calls `work_order.collaborators.set(worker_hours.keys())` so the M2M can never disagree with the hours rows about who worked the job. Naming the same person on two rows sums their hours rather than tripping the `unique_worker_hours_per_work_order` constraint. `collaborator_queryset` in `workorders/forms.py` excludes the job's author (you can't collaborate with yourself) and, when a plain worker is the one filling the form in, anyone who isn't also a `WORKER` — see the two-argument rule above. The one place the two *can* drift is the admin: `WorkOrderAdmin` exposes the `collaborators` multi-select and the `WorkerHoursInline` as independent widgets, so an admin edit can leave a collaborator with no hours row, or vice versa.

**A machine stores no totals.** There used to be a `Machine.total_hours` counter kept in sync by `MachineUsage.save()`/`delete()` with `F()` updates and a `select_for_update()`, and with it a standing rule against `bulk_create`/`queryset.update()`/`queryset.delete()` and against letting a `WorkOrder` cascade onto a usage row. **No page read it** — and it counted unapproved jobs, so it never agreed with Stroje anyway — so migration `materials.0011` dropped the column and both model methods. `MachineUsage` is an ordinary model now, and `_write_job_rows`/`job_delete` bulk-delete their rows. `_machine_summary` annotates `Sum('usages__hours')` **and `Sum('usages__tons')`** over the rows the page's own filter allows (`usages__in=usages.values('pk')`), so the totals and the detail rows below them can never disagree, and both respect the review status. **Every active machine is listed**, not just the ones with rows in range — with no filter that is the whole fleet, and under a date filter a machine sitting at `0 h` answers "what ran last week" — except that naming a machine in the filter narrows the table to it. An invalid filter returns `Machine.objects.none()`, the same rule the rows follow.

`_time_worked_summary` in `workorders/views.py` sums `WorkerHours.hours` per user over the scoped work orders. The view re-queries by `pk__in` into `scoped` before aggregating, because the collaborator filters join the M2M and would otherwise multiply the `Sum`. Two separate scoping steps, both needed: the *queryset* is narrowed by `_participation_filter` (created-by or collaborator) so a worker only sees jobs they took part in, and then the summary **rows** are filtered again to `row['user'] == request.user` — without that second pass a collaborated job would put the creator's hours on a worker's screen.

All pages are mobile-first templates under `templates/workorders/`. **The Zpracování form's body is one partial, `_job_form_fields.html`** — the job's own fields plus the four formset sections — included by both `transform_form.html` and `job_edit.html` inside each page's own `<form>`, so a field added to a formset row cannot land on one page and be forgotten on the other; only the heading, the submit button and the *Zpět bez uložení* link stay with the caller. It carries no `<form>` tag, no `{% csrf_token %}` and no button. Two things let one partial serve both pages: „Zapsat za" sits behind `{% if order_form.author %}`, false on `job_edit` because that view builds `WorkOrderForm` without a `user` so the field is never added; and the hours label is read off the form instead of being written into the markup, because `job_edit` overrides it to „Hodiny – <author>" (a manager correcting someone else's job is looking at neither „Moje hodiny" nor a bare „Odpracované hodiny"), set after both branches since an invalid POST re-renders too. Login and password-change are Django's own generic views, wired in `config/urls.py` with the Czech `CzechAuthenticationForm`/`CzechPasswordChangeForm` from `accounts/forms.py` and templates under `templates/registration/` — `accounts/views.py` is empty and there is no `accounts/urls.py`.

The bottom nav is hardcoded in `templates/base.html` and needs a new page's entry added by hand. Workers see Zpracování / Hodiny; **Přehled and Stroje are inside `{% if user.is_manager_or_admin %}`**. The `/jobs/` review views **and `machine_dashboard`** are gated with `@role_required(User.Role.MANAGER, User.Role.ADMIN)`, so a worker who types one of those URLs gets a 403. Hiding a link is not access control; if a page is meant to be manager-only, gate the view too. Stroje was nav-only for a while and is not any more. **The gate replaced its worker scoping rather than layering on top of it**: `_filtered_machine_usages` no longer filters by `_participation_filter`, and `MachineFilterForm` lost its `__init__` (and its `user` kwarg) along with the `del self.fields['created_by']`, because nobody who can reach the view is scoped. Everyone past the decorator sees the whole depot. `MachineUsageDetailTests` asserts the 403 instead of the scoping it used to cover. Relaxing the gate means writing both halves back.

Page-scoped CSS is keyed off the URL name: `base.html` renders `<body class="page-{{ request.resolver_match.url_name }}">`. So **renaming a URL name silently drops that page's styling** — grep `static/css/app.css` for `.page-` before touching `urlpatterns`. There is no test covering the pairing. (No `.page-` rule survives the stock removal, so the file is currently empty of them.)

Two cross-cutting patterns that every list view follows; match them in new views rather than inventing a variant (`job_dashboard` follows the second one; the first does not apply to it, since the whole view is manager-only and there is nothing to scope):

- **Worker scoping is enforced in the view queryset, not by hiding fields.** `time_worked` filters to `Q(created_by=user) | Q(collaborators=user)` for non-manager/admin users, *and separately* `del`s the `worker` field in `TimeWorkedFilterForm.__init__`. The `del` is only cosmetic — the queryset filter is what makes `?worker=<someone else>` a no-op, and `test_worker_cannot_bypass_restriction_via_worker_param` asserts it. **`time_worked` is the only page this still applies to**: it is the one filtered list a worker can open. `machine_dashboard` used to follow it and no longer does — see the role gate above. Follow the pattern in any new worker-reachable list view, and don't add it to a `role_required` one, where it is unreachable by construction.
- **Every filter form gets the quick date ranges.** `_date_preset_links(request)` in `workorders/views.py` builds them from `DATE_PRESETS` (Vše / posledních 7 dní / posledních 30 dní / minulý měsíc); all three filtered pages pass the result as `date_presets`, and the row itself is `templates/workorders/_date_presets.html`, included at the top of each filter card. They are **plain links that set `date_from`/`date_to` in the querystring**, not a form field — one tap on a phone, no JS, and because the form is bound afterwards the chosen range shows up in the two date inputs. Each link copies the rest of `request.GET` (so the machine or worker already picked survives) and drops `page` (a new range starts at page one). Dates go in as ISO, which `cs` parses because Django appends `%Y-%m-%d` to every locale's `DATE_INPUT_FORMATS`. The spans include today, so „posledních 7 dní" is today plus the six before it; „Vše" removes both parameters and is the way back out of a range on a phone, where emptying a date input by hand is fiddly. A new filtered page needs the context key *and* the include — neither half works alone.
- **An invalid filter form returns `.none()`, never the unfiltered queryset.** Silently ignoring a bad filter would hand back everything under a "these are your filtered results" heading. An *unbound* form (no querystring at all) does show everything — the distinction is `form.is_bound`, checked before `form.is_valid()`.

Superusers bypass role checks in two places — `role_required` and `User.is_manager_or_admin` — because `createsuperuser` never sets a `role`, so a bootstrap admin would otherwise default to `WORKER` and be locked out of the app it administers.

User-facing copy (auth forms in `accounts/forms.py`, form labels/`empty_label`s in `workorders/forms.py`, the `RETIRE_HELP_TEXT` block in `materials/models.py`, model `TextChoices` labels, etc.) is written in Czech for depot workers by **hardcoding Czech strings/labels directly** rather than going through Django's i18n framework — keep new user-facing text in the same style rather than introducing `{% trans %}`/`gettext` half-way.

`LANGUAGE_CODE = 'cs'` and `TIME_ZONE = 'Europe/Prague'` cover the parts the app doesn't write itself. The language setting is what makes **Django's own** strings Czech — admin chrome, `contrib.auth`, and form validation errors (`Toto pole je vyžadováno.`, `Zadejte číslo.`) — using the `.mo` catalogs Django ships. `LocaleMiddleware` is deliberately *not* installed, so the language is fixed rather than negotiated per-request from `Accept-Language`. The two mechanisms are complementary: the setting handles framework strings, hardcoding handles app copy.

Consequences of the locale worth knowing before you touch numbers or dates:

- **Template output of numbers is localised** — `{{ row.hours }}` renders `12,50`, not `12.50`. Tests that assert on rendered quantities must use the comma. `|floatformat:N` localises too, so `{{ machine.filtered_hours|floatformat:1 }}` renders `6,0 h`. Form inputs are *not* localised (fields default to `localize=False`), so `NumberInput` still renders and accepts `value="12.50"` with a dot, and a comma typed into a `DecimalField` is rejected with `Zadejte číslo.` Leave it that way — setting `localize=True` would downgrade the widget from `<input type="number">` to a plain text input and cost mobile users their numeric keypad.
- **Date input still round-trips.** Czech `DATE_INPUT_FORMATS` is `%d.%m.%Y`-first and does not list ISO, but Django appends `%Y-%m-%d` to every locale's list, so the `<input type="date">` widgets on the filters parse normally. Bound forms re-render the raw submitted string, so filters survive pagination. **The trap is an *unbound* date field with a python-`date` `initial`**: it renders as `14.08.2026`, which an `<input type="date">` rejects as invalid and shows blank. `WorkOrderForm.performed_on` is exactly that — pre-filled with today, and pre-filled with the job's own date on `job_edit` — so its widget passes `format='%Y-%m-%d'` explicitly. Any new pre-filled date field needs the same.
- **Every `ModelChoiceField` needs an explicit `empty_label`.** Django 6 defaults it to `- Select an option -`, which is *not* a translatable string — it renders English even under `cs`, so it cannot be fixed by the locale. The transform formset rows in `workorders/forms.py` use the bare noun instead — `Materiál` / `Stroj` / `Pracovník` — because each row renders the selects side by side with no room for a visible label, so the empty option *is* the label (and for the same reason `hours` on those rows carries a placeholder instead). Filter forms (`MachineFilterForm`, `TimeWorkedFilterForm`, `JobFilterForm`) use an "all" phrasing, since a blank there means "don't filter": `Všechny stroje`, `Všichni pracovníci`, `Všichni uživatelé`. `EmptyLabelTests` in `workorders/tests.py` fails if a new field forgets. `ModelMultipleChoiceField` (e.g. `collaborators`) has no blank option and needs nothing.
- **Time is 24-hour everywhere the app renders it** — templates use `H:i` and Czech `TIME_FORMAT` is `G:i`. The app no longer renders a `<input type="datetime-local">` anywhere; that widget was the one place the browser, not the app, picked the format (an English-configured phone showed AM/PM regardless of `lang="cs"`), and it went with the Příjem/Výdej back-dating checkbox. If you reintroduce one, that caveat comes back with it.
- **Keep explicit date formats in templates.** Timestamps use `|date:"Y-m-d H:i"`, which is locale-independent; a bare `{{ ... }}` on a date would render as `14. srpna 2026` instead.
- **`USE_TZ` stays on, so the DB still stores UTC** — `TIME_ZONE` only affects rendering. No filter depends on it any more: the date filters compare `WorkOrder.performed_on`, which is a `DateField` with no time and no zone, so a job recorded at 00:30 local cannot land on the previous UTC day the way a `created_at__date` lookup could. Python code does *not* auto-localise, so anything formatting a datetime outside a template needs `timezone.localtime()` explicitly. Nothing does today; the CSV export that did was removed.

**The Django admin is fully Czech too, via three separate mechanisms** — a new model or admin needs all three or it will show English in one place:

1. **App labels** — `verbose_name` on each `AppConfig` (`Katalog`, `Zakázky`, `Uživatelé`; `inventory` carries `Zpracování` but registers nothing, so it is not shown), which is what the admin index groups by. Those three are the whole index: **`auth.Group` is unregistered** in `accounts/admin.py`, which also takes Django's own `Autentizace a autorizace` section with it. Permissions play no part in this app — access is `role` + `role_required`, and every account that can reach the admin is a superuser, which bypasses permission checks — so a group could only ever be a no-op mistaken for access control. `CustomUserAdmin` had already dropped `groups`/`user_permissions` from its `fieldsets`; this is the last trace. Nothing is deleted, and re-registering restores it.
2. **Model and field names** — Czech `verbose_name`/`verbose_name_plural` in every `Meta`, and an explicit lowercase `verbose_name` on every field (Django capitalises it where needed). Adding one is a migration: `makemigrations` emits `AlterField` for a pure label change, and CI fails without it.
3. **`LOCALE_PATHS` → `locale/cs/LC_MESSAGES/django.po`** for the handful of *Django's own* strings whose `cs` translation Django doesn't ship — `- Select an option -`, the delete-confirmation sentence, the date-hierarchy label (rendered by `WorkOrderAdmin`, the one admin with a `date_hierarchy`), the two screen-reader-only `Search %(name)s` / `Pagination %(name)s` headings. These are not fixable by `LANGUAGE_CODE`, because the msgid simply isn't in the catalogs Django installs. This is the one place the project *does* use the i18n framework, and it holds Django msgids only — app copy stays hardcoded.

The catalog is read from the **compiled `.mo`, and both files are committed**; editing the `.po` alone changes nothing at runtime. Recompile with `python manage.py compilemessages -l cs --ignore=.venv` — without the `--ignore` it walks into the virtualenv and recompiles every catalog Django ships. `AdminCzechTests` in `accounts/tests.py` fails if the `.mo` is missing or stale, so CI catches a forgotten recompile.

What this *can't* reach: `filter_horizontal`. Its widget builds labels in JavaScript from the `djangojs` catalog, and the admin's `jsi18n` view loads only `django.contrib.admin`'s own locale dirs — `LOCALE_PATHS` is ignored there, so three untranslated strings ("Choose %s by selecting them…") would render English. `WorkOrderAdmin` therefore uses the plain multi-select for `collaborators`; don't reintroduce `filter_horizontal` without checking that.

Run a single app's tests, or a single test case/method, the same way:

```bash
python manage.py test materials
python manage.py test materials.tests.MaterialModelTests.test_material_str
```

Tests are one `tests.py` per app, plain `django.test.TestCase`, no pytest and no mocking — almost everything drives a real view through `self.client` and asserts on both `response.context` and the resulting rows. Postgres is required; there is no SQLite fallback, and no separate test settings module, so a change to `config/settings.py` (locale included) is a change to how the suite behaves.

`inventory/tests.py` is now model-level only — the app has no views to drive. Everything that exercised a request path moved out with the stock pages; `workorders/tests.py` is where the app is actually covered.

The suite has **no `TransactionTestCase`, and needs none**: there is no concurrent write path left. `StockLockConcurrencyTests` went with the stock pages, and the last `select_for_update()` went with `Machine.total_hours`. Every write is now a plain insert or delete whose outcome does not depend on what another request is doing. Add a counter or any other read-modify-write and that changes — a plain `TestCase` wraps the whole test in one transaction and hides the interleaving, so such a test has to be a `TransactionTestCase`.

Seed the material catalog, machinery, and employee accounts from CSV (idempotent — safe to re-run; matches the `.env`/`.env.example` pattern, real files are gitignored):

```bash
cp seed_data/materials.example.csv seed_data/materials.csv
cp seed_data/machines.example.csv seed_data/machines.csv
cp seed_data/users.example.csv seed_data/users.csv
# edit those three files with real data, then:
python manage.py seed_data
```

`machines.csv` takes `name,hourly_rate,rate_per_ton` — a machine stores no hours to seed; Stroje sums them from the approved usage rows on every render. `materials.csv` takes `sku,name`. **A material carries nothing else** — `category` and `unit_of_measure` were both removed (migrations `materials.0009` / `materials.0010`, which drop the columns and their values). **Every quantity in the app is tonnes**, implicitly: there is no unit field to read, so the `t` in the form prompt („Množství (t)"), the job detail table and `StockMovement.__str__` is hardcoded. `csv.DictReader` ignores columns the command does not read, so an older CSV that still carries the retired ones keeps working.

The optional `hourly_rate` and `rate_per_ton` columns are only written when the CSV actually carries a value for that row: omitting the column, or leaving the cell blank, **preserves** whatever is already in the database, so re-seeding never clobbers a rate someone set by hand in the admin. New records still fall back to the model default (`NULL` for both). Clearing a value back to empty is an admin action, not a CSV one.

New users get a random temporary password printed to the console (share it securely); only `ADMIN`-role users get Django admin access — both `is_staff` (to log in) and `is_superuser` (to actually see/edit anything there; `is_staff` alone gets an empty "you don't have permission" admin index). Managers do not get admin access at all — what distinguishes them in the app is `is_manager_or_admin`: the Stroje nav entry, and an unrestricted view of everyone's hours and machine usage rather than just their own.


CI (`.github/workflows/ci.yml`) runs `ruff check` and `ruff format --check` (must pass, not just run), a `docker build` sanity check, and a test job as separate jobs on every push/PR. The test job is three steps, not one: `manage.py check`, then `manage.py makemigrations --check --dry-run`, then `manage.py test`. That middle step means **a model change without its migration file fails CI even if every test passes** — run `makemigrations` and commit the result alongside any `models.py` edit. Both triggers carry a `paths-ignore` list, and as of `30c6477` it is **`'**.md'` and nothing else** — a commit touching only Markdown runs **no jobs at all**, so don't wait for a green check on such a push and don't take one as evidence the code still builds. Everything else, dotfiles and `.github/` included, now triggers the full pipeline. Beware that the comment block above `on:` in `ci.yml` still describes the four removed dotfile globs (`.*`, `.*/**`, `**/.*`, `**/.*/**`) as if they were live; read the `paths-ignore` keys themselves, not the comment. Dependabot (`.github/dependabot.yml`) opens weekly update PRs for pip, Docker base images, and the Actions themselves.

## Deployment

Only the dev-oriented `docker-compose.yml` exists today (`runserver`, `DEBUG=True`, DB port exposed). A LAN-only production deployment to a company server is planned but not yet implemented — see [DEPLOYMENT_PLAN.md](DEPLOYMENT_PLAN.md) for the approach.

Both blockers that plan identified are now **fixed** (its Context section records the reasoning; sections 3-6 — prod compose file, `.env.production.example`, backup script, runbook — are still to do).

Static files are the part most likely to trip you up, because the correct behaviour differs per environment:

- **`WhiteNoiseMiddleware` is in `MIDDLEWARE` unconditionally**, in every environment including the test run — only the *storage backend* is environment-dependent. So "is whitenoise active?" is the wrong question; the one that matters is which of the two backends is live.
- **The static backend is chosen by `STORAGES['staticfiles']`, driven by the `STATICFILES_BACKEND` env var**, defaulting to plain `StaticFilesStorage`. It is *not* `STATICFILES_STORAGE` — Django removed that setting in 5.1, and it sat in this file being silently ignored until it was migrated. If you ever need to know which backend is really live, check it, don't read the setting: `from django.contrib.staticfiles.storage import staticfiles_storage; type(staticfiles_storage)`.
- **The default is plain storage specifically so the test suite works.** Whitenoise's manifest storage rewrites every `{% static %}` URL to a hashed name looked up in `staticfiles.json`, and raises when there's no manifest — non-strict mode doesn't save you either, since it falls back to hashing the file and that file isn't in `STATIC_ROOT` without a `collectstatic` run. Django's test runner forces `DEBUG=False`, and `DEBUG` is precisely what short-circuits the hashed-URL lookup. So flipping the default to manifest storage makes **every test that renders a template** fail with `ValueError: Missing staticfiles manifest entry`. Don't.
- **Production opts in through the `Dockerfile`,** which sets `ENV STATICFILES_BACKEND=...CompressedManifestStaticFilesStorage` and then runs `collectstatic`. Keep those two together: the `ENV` persists into the running container, so the backend that writes the manifest and the one that reads it can't drift apart. Setting the backend in `.env.production` instead would reintroduce exactly that split.
- **`static/` is source, `staticfiles/` is generated.** `.gitignore` used to ignore the former, which is why `static/img/background.jpg` — referenced by `static/css/app.css`, which every page loads — was missing from the repo for a while. New assets go in `static/` and must be committed.
- **Don't park non-assets under `static/`.** `collectstatic` publishes everything there at an unauthenticated `/static/` URL. `static/xlsx/` holds a working spreadsheet and is excluded in both `.gitignore` and `.dockerignore` for that reason; it would be better off outside `static/` altogether.
- **CI does not cover any of this.** The `docker build` job would catch a `collectstatic` failure, but the test job runs with plain storage and never requests a static URL. Verify static changes by running the built image with `DEBUG=False` and curling an asset.
